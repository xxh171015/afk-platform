# AFK 平台优化建议与实施计划

2026-11-05 · 基于当前代码与设计文档的静态评估；2026-11-06 起 P0/P1 按现有实现收紧；2026-11-06 第二轮：按平台方向和一次调度复现，补充 1.4–1.8、2.5–2.9、3.4–3.8；2026-11-10 第三轮：M3 合入后按四个目标复查代码和 Mac 上的真实运行记录，补充第 4 节；2026-11-12 第四轮：复盘 S-28 在 Mac 上的运行，补充第 5 节；2026-11-12 第五轮：按 agent 自己做的决定复查执行阶段的设计，补充第 6 节；2026-11-12 第六轮：按健壮性和 token 用量复查真实运行记录，补充第 7 节；同日重新 grill 第五、六轮，结论收进 spec #262（票 #263–#273）和 [ADR 0010](adr/0010-afk-means-do-not-wait.md)，第 6、7 节已按结论改写

## 定位与结论

AFK 平台已经具备「规划与拆票 → 按依赖调度 → 沙箱执行 → 门禁与收尾 → 人工验收」的主链路。现有实现中，作业租约与 fencing、真实 Postgres 测试、按包划分的依赖方向、结构化简报和工作台，都是值得保留的基础。

第一轮的四项（1.1、1.2、2.1、2.2）已经在 #186 里实现，随 PR #192 合并。第二轮有两个新的出发点：

- **平台方向。** 2026-11-06 的讨论确定：平台要给本部门 4–5 个团队共用，仓库语言不限，目前可以把代码发给外部模型，运营归属以后再定。排在最前面的是地基：共享部署、多 worker、GitLab 适配器和 webhook、GitLab 登录、IM 通知、基础度量。第二轮按这个顺序排，给其他团队用之前必须有的，优先级往前提。
- **一个调度缺陷。** 同一个项目里先后确认两个需求，后确认的那个可能一直不开工（2.5，已在真 Postgres 上复现）。多需求并行是 M3 的验收条件，这一条排在最前面。

优化应服务于三个结果：**人被叫回来时能迅速做对决定**，**需求、Run 和日志积累后仍能稳定使用**，以及**能用数据说明平台在多个团队里好不好用**。本文是优化建议，不替代 [总体设计](design.md) 或 [操作体验 spec](specs/experience-platform.md)；涉及 M3–M5 的建议以现有里程碑为前提。术语以 [GLOSSARY](../GLOSSARY.md) 为准。

第三轮在 M3 合入 main（PR #237）之后，按四个目标复查：用平台的人配置起来顺手；平台做出来的效果不比手动用 matt skills 差；没有明显的逻辑漏洞；性能还能再省。这一轮第一次有了真实运行记录可看（用户 Mac 上平台库的只读统计，16 个需求、204 次 Run），结论见第 4 节：提示词写死了 npm 命令，非 Node 仓库会跑错；票级审查 50 次没有提出一条必须修的问题，需求级审查却抓到 4 条；push 失败没有重试，网络抖一下就白跑一小时 agent；纯 GitLab 团队在 afk-setup 第一步就被拦住；托管同步每分钟对全部历史需求拍快照。

第一轮只读了代码和文档。第二轮同样以读代码为主，另用一次性测试复现了 2.5，跑过 typecheck 和 lint。第三轮另读了真实运行记录，并在 Linux 沙箱和 Mac 上各跑了一遍全量检查（4.16）。三轮都没有开展真实用户走查、运行压测或生产故障分析。因此性能问题是有代码依据的风险，具体阈值须先测量，不能当作已发生的故障；第三轮的数字样本小，用来定方向，不当基线。

## 1. 用户体验优化

### 1.1 待处理队列：在现有卡片上给出排序和影响（P0）

**状态。** 已实现（#187），随 PR #192 合并。

**现状。** [待处理页面](../packages/web/src/BlockedQueue.tsx)对应的是 [待处理队列](../GLOSSARY.md)，不是 Ticket 状态 `pending`。`GET /blocked` 按类别返回七组数组，组内按 Serial ID、组间按固定类别顺序拼接；没有跨类别排序，也没有「阻断了什么」。结构化简报已覆盖原因码、步骤、证据和建议动作；卡上已有重试、改正文、批准保护路径和危险操作确认。工作台「等你处理」和通知深链到票页 / 交付页 / 需求页，不进入 `/waiting`。下游尚未 done 的 Ticket 可由 Edge 现算，但 API 不返回。没有 `blocked_at`。

**建议。** 不重做卡片，不改结构化简报的类型，不新增 priority 字段，不让模型排序。每张卡只加两行：「阻断了什么」和「为何排在这」。五槽（发生了什么 / 阻断了什么 / 建议动作 / 证据 / 可执行动作）是读法，不是新实体。

「阻断了什么」现算、不存库：

- 票：同 Spec 沿 Edge 尚未 done 的下游 Ticket 显示编号；若因此收尾不能开始，写上
- 收尾 / Final e2e：挡住开 PR
- 暂停的 Spec / 规划 blocked：整份 Spec
- PR / 转 ready 失败：挡住合并进 main
- 清理失败：不挡住其他 Ticket

排序全比较、稳定：挡住尚未 done 的下游 Ticket → 挡住收尾或开 PR → 挡住合并进 main（暂停的 Spec 与规划 blocked 同档）→ 等待更久 → Serial ID 升序。`plat blocked` 用同一顺序。可选「按需求收拢」：同一 Spec 的事项挨在一起，组与组之间按组内最高优先级排。保留原有类别筛选。不按仓库收拢。

等待起点不新增列：票和收尾用最近一次相关 Run 的 `finished_at`（没有则该行 `created_at`）；暂停的 Spec 用该 Spec 最近一次 Run 的 `finished_at`（没有则 Spec `created_at`）；PR / 清理用对应行已有时间。`GET /blocked` 返回这些现算字段。工作台 P0 仍深链，不改成展示简报。

第一刀只读：不新增清理、规划重试、取消 Spec、追加等页面写操作（仍走 `plat`）；卡上已有动作保留。

**实施步骤。**

1. 在 `GET /blocked` 增加现算的 `waitingSince` 和 `blocking`（下游显示编号、是否挡住收尾/开 PR），保留原始原因码和 Run 指针。
2. 待处理页按上述规则排序并加上两行说明；实现按需求收拢。
3. `plat blocked` 改为同一顺序。先上线只读排序与说明，再根据实际操作记录调整规则。

**验收。** 从通知或工作台落到具体事项时，不必先打开多张详情页，就能知道为何优先、该做什么、证据在哪、挡住了哪些显示编号。操作后卡片消失，或明确说明仍被什么阻断。记录「通知到首次操作」和「通知到恢复运行」的时间分布，作为改进依据。

### 1.2 首次接入：本机与接入条件分开展示（P1）

**状态。** 已实现（#189），随 PR #192 合并。

**现状。** [接入入口](../packages/web/src/Onboarding.tsx)挂在工作台上，只提供锁定版本的安装命令和 `/afk-setup` 指引。`GET /projects` 失败时仍显示折叠的「接入新项目」，和「已经有项目」无法区分。页面不读仓库列表，也不调用 GitHub App access。规划机器上的 skills / plat / Tracker doc 没有 HTTP 接口。GitHub App 的 access 能看到门禁文件和联调 compose 是否存在，看不到 `AGENTS.md`。`gate-check` 作业能跑门禁是否通过，但结果不存成仓库状态。

**建议。** 清单分两段，不用「就绪检查」这种叫法。

- **本机**（规划机器）：skills、plat、Tracker doc。API 查不到，标「尚未检查」，给出可复制命令。
- **接入条件**（[Repo readiness](../GLOSSARY.md)）：`GET /version` 表示平台可达；项目和仓库列表表示已登记；`GET .../access` 表示 GitHub App 权限以及门禁文件、被联调依赖仓库的 compose 是否存在。`AGENTS.md` 属于接入条件，但 access 看不到：放在仓库段，标「尚未检查」并给命令，不放进本机段。

项目数读取失败必须显示错误和重试，不能看起来像已经有项目。页面读上次 access；GitHub 仓库提供「现在检查」按钮（`POST .../access-check`），不要每次打开工作台自动打 worker。GitLab 写明仅 GitHub 可查。不从页面跑 `gate-check`（门禁是否通过仍是 `plat repo check`）。

**实施步骤。**

1. `GET /projects` 失败时展示错误和重试；成功且数量为零时再展示「接入第一个项目」。
2. 按两段渲染清单：本机全部「尚未检查」+ 命令；接入条件绑定已有 `GET /version`、项目/仓库、`GET .../access`。
3. GitHub 仓库加上「现在检查」；GitLab 标明不可查。

**验收。** 新用户能从页面判断卡在本机还是接入条件的哪一步；API 故障不会被误认为接入完成；GitHub App 检查由人点按钮触发；所有「尚未检查」都对应一条可复制命令。

### 1.3 窄屏：提供任务视图（P2）

**现状。** [需求列表](../packages/web/src/SpecList.tsx)在窄屏下保留最小宽度 1200px 的表格并横向滚动；样式文件仅对侧栏、顶栏等做了收缩。当前桌面优先的定位是合理的，但小屏阅读和处理会比较费力。

**建议。** 在窄屏下用卡片显示编号、标题、状态、进度和下一步；完整列留在桌面表格。优先保证「查看待处理、打开证据、执行简单恢复动作」，不必把依赖图编辑等桌面任务搬上手机。

**验收。** 320–640px 宽度下，查看待处理和进入票详情无需水平滚动；主要按钮可触达，长标题和错误信息不会遮挡操作。

### 1.4 人不在这台 Mac 前也能收到通知（P1）

**状态。** 2026-11-09 M3 范围调整后挪到 M4（飞书通知），M3 只在 Mac 本机用。

**现状。** 通知只有一个渠道：API 进程在本机用 `osascript` 弹 macOS 横幅（[notify/channel.ts](../packages/api/src/notify/channel.ts)）。人不在这台电脑前就收不到；正文里的链接是本机页面地址（默认 `http://127.0.0.1:5173`，见 [page-url.ts](../packages/api/src/page-url.ts)），换一台设备打不开。平台要让人离开，而需要人回来的那一刻，人往往正好不在电脑前。操作体验 spec 当时把 webhook 列为不做；平台方向把 IM 通知放进了第 0 步，这里按后者。

**建议。** 渠道已经是适配器（`NotificationChannel`），加一个群机器人 webhook 渠道（飞书、企业微信、钉钉先选一个），和 macOS 横幅并存。七类事件、标题和一句原因都不变；正文另附平台外也能打开的链接：有 PR 的附 PR 地址，页面地址在平台部署到服务器之前注明「本机」。webhook 地址按项目配置，和其他密钥一样不进库。不做收件箱，也不做在消息里直接重试或放行（那要登录和权限，归 2.4）。2.6 做好后，通知改为从事件表发，同一个事件只发一次。

**实施步骤。**

1. 加 webhook 渠道和配置项；测试用假 HTTP 服务，不真发。
2. 正文加上 PR 地址；页面地址是本机地址时注明。
3. 上线后看一周的消息量，再决定要不要把同一需求短时间内的多条合成一条。

**验收。** 人不在电脑前时，手机上能收到「T-n 卡住」「可以来验收了」这类消息，PR 链接能打开；macOS 横幅照旧；webhook 发送失败只记日志，不影响状态流转。

### 1.5 能自己恢复的失败先自动重试一次（P1）

**状态。** 未做。2026-11-10 的运行记录里，implement 和 review 各有一次空闲超时，都直接进了待处理队列。

**现状。** 实现和各种修复阶段的 `timeout`、`invalid-output`，以及 review、诊断阶段的同类结果，都直接进 blocked、叫人回来（[stage-flow.ts](../packages/shared/src/stage-flow.ts) 的 `advanceStage`）。这两类多半是模型或网络的偶发问题：agent 沉默超过空闲上限，或者最后没有按格式输出 `<result>`。作业层面的失败（沙箱起不来、推送被拒）已经会自动重排，最多三次（[failures.ts](../packages/api/src/stages/failures.ts) 的 `MAX_JOB_FAILURES`）；agent 结果层面没有这一层。

**建议。** 给这两类结果每张票一次自动重试的额度，和 fix 次数一样记在票上：第一次出现时按 `continue` 重排同一阶段，附一条平台写的 Retry note，例如「上次运行超时，分支上的提交保留，从它们接着做」「上次没有输出 `<result>`：检查分支上已有的提交，按格式补上结果」；第二次才进 blocked。`no-commits`、`agent-gave-up`、`contract-change-needed` 本来就要人决定，不在其中。重试花的时间照样计入需求的 agent 时长预算。自动重试记成事件（2.6），度量里把「自动恢复」和「人处理」分开统计。

**实施步骤。**

1. `advanceStage` 增加自动重试的决定，`Progress` 记已用次数；人重试时清零，和 fix 次数一致。
2. API 应用这个决定时写入平台生成的 Retry note，下一次 Run 从 `/context/note.md` 读到。
3. 简报和时间线上标明「已自动重试一次」。

**验收。** 人为制造一次超时和一次缺 `<result>`：各自动重试一次，第二次仍失败才进待处理队列；需求的 agent 时长包含重试的时间；人重试后额度重新计算。

### 1.6 卡住之后：一份简报三处同用，下一步给到命令（P2）

**状态。** 已实现（S-19，PR #236），这是平台自己跑出来的第一个需求。

**现状。** 「卡在哪、证据是什么、该怎么做」的解读只在页面里：[structured-brief.ts](../packages/web/src/structured-brief.ts) 从 Run 的原始输出里挑证据，建议动作是按原因码写死的一句话。`plat blocked` 打印的是原始简报（[format.ts](../packages/cli/src/format.ts) 的 `briefLines`），macOS 通知又有自己的一句原因（[notices.ts](../packages/api/src/notify/notices.ts)），三处说法不一样。只能走 `plat` 的动作在页面上也只有一句话，比如 `contract-change-needed` 是「先改提供方契约票，再继续」，具体怎么追加要人自己拼命令。

**建议。** 把结构化简报的生成挪进 `@afk/shared`（它本来就是纯函数），由 API 在待处理队列和票详情里返回，页面、`plat blocked`、通知（包括 1.4 的 IM）都用这一份。每个原因码在一句建议之外，再给出填好编号、可复制的命令：`gate-failed` 给 `plat ticket retry T-n --mode continue --note "…"`；`protected-path-changed` 给 `plat ticket approve-protected T-n` 和随后的 retry；`contract-change-needed` 给 `plat tickets import S-n <目录> --append`，并附一份用 agent 的 `detail` 预填的新契约票草稿（`blocked_by` 旧契约票，`blocks: [T-n]`）。页面不新增写操作，只多一个复制按钮，和 1.1「第一刀只读」一致。

**实施步骤。**

1. 简报生成移到 shared，由 API 返回；页面改为直接渲染，删掉页面里的解读。
2. 按原因码补上下一步命令；`contract-change-needed` 生成票草稿。
3. `plat blocked` 和通知改用同一份简报。

**验收。** 同一张卡住的票，页面、`plat blocked` 和通知给出的结论、下一步一致；`contract-change-needed` 的票能复制命令和草稿，按草稿追加之后原票能接着跑。

### 1.7 `plat doctor`：本机检查的结果回到页面上（P2）

**现状。** 1.2 把接入清单分成本机和接入条件两段，本机一段（skills、plat、Tracker doc）API 查不到，一律标「尚未检查」并给命令。这些检查现在散在 afk-setup、`plat update` 的过期提示、`plat spec create` 和 `plat tickets import` 之前的核对里，没有一条命令能一次说清这台机器缺什么。接入条件里的 `AGENTS.md`，GitHub App 的 access 看不到，本机的 checkout 却看得到。

**建议。** 加 `plat doctor`：在规划仓库里一次检查本机（Node、git、`gh` 登录、plat 和平台的版本、skills 的版本和安装级别、Tracker doc 是否最新、本机规则文件），以及工作区里各仓库在本机看得到的接入条件（默认分支或 `afk/setup` 上有没有 `gates.yaml`、`AGENTS.md`）。每项给出通过、缺什么、修复命令；`--json` 给 skill 用。结果按机器上报给平台，只存最近一次，接入入口的本机一段就能显示「<机器名> 已检查 · 3 分钟前」。afk-setup 最后一步改成跑它。其他团队排障时，这是第一条要跑的命令。

**实施步骤。**

1. 把分散的检查收进 `plat doctor`。
2. 加上报接口（按项目和机器名存最近一次结果），接入入口读它。
3. afk-setup 和操作手册改为用它收尾。

**验收。** 分别在缺 skills、Tracker doc 过期、缺 `AGENTS.md` 三种情况下运行，`plat doctor` 各给出一行原因和命令；运行过之后，接入入口的本机一段显示结果和时间，没运行过的仍是「尚未检查」。

### 1.8 页面确认不悄悄丢掉规划文档（P2）

**现状。** 规划文档（GLOSSARY、ADR）只有在规划仓库里用 `plat spec confirm` 才会带给平台（ADR 0005）。页面不知道本地有没有改动，所以凡是有规划仓库的需求，确认前预检都显示同一条黄色提示（[views.ts](../packages/api/src/tickets/views.ts) 的 `PAGE_CONFIRM_WITHOUT_PLANNING_DOCS`）。没有改动时这条提示是噪音；有改动时人看惯了也会点过去，这次 grill 写下的术语和决策就进不了集成分支，agent 也读不到。

**建议。** 先做轻的一步：`plat tickets import` 本来就在规划仓库里运行，导入时顺手记下规划文档有没有本地改动、改了哪些文件（只记文件清单，不传内容）。没有改动就不出提示；有改动时，预检和确认对话框写明「导入时规划仓库里有 3 处规划文档改动（GLOSSARY.md、docs/adr/0008-…），页面确认会丢掉它们，请在规划仓库里运行 `plat spec confirm S-n`」，仍要在页面确认得再点一次。导入之后才改的，页面仍然看不到，所以提示写明「导入时」；导入不是在规划仓库里运行的，不知道有没有改动，照现在这样出通用提示。重的一步（导入时就上传补丁，页面确认也能做规划提交）牵涉确认后由谁把本地副本收走（#176 的零残留），先 grill 再定。

**实施步骤。**

1. 导入请求带上规划文档的改动清单，存到需求上。
2. 预检和确认对话框按清单出提示；没有改动时不出。

**验收。** 规划仓库里有未提交的规划文档时导入，页面确认前能看到文件名和命令；没有改动时预检里没有这一条；CLI 确认的行为不变。

## 2. 架构优化

### 2.1 列表与工作台查询按用途收敛（P1）

**状态。** 已实现（#190、#191），随 PR #192 合并。

**现状。** [需求列表查询](../packages/api/src/tickets/views.ts)聚合所有 Spec 和票，没有分页；前端再完成筛选、排序。[工作台查询](../packages/api/src/tickets/workbench.ts)复用全量 Spec 列表，并把完整待处理队列（含 brief）塞进 `waiting`，再对历史 Run 按项目和阶段做全表均值。侧栏角标为了计数也拉全量 `GET /blocked`。面包屑的 Spec 切换器同样拉全量 `/specs`。SSE 的 `invalidate` 只带 spec / ticket / run id，随后这些查询整份重拉。小规模时逻辑清楚，规模增长后每次刷新都要重复处理历史数据。

**建议。** 先用代表性数据测量 `/specs` 和 `/workbench` 的数据库耗时、响应体积及页面首次可操作时间。随后切开耦合，不要先做缓存表：

- 工作台不再复用全量 Spec 列表；直接查当前运行、待验收和最近完成的有限集合。`waiting` 只留显示编号、标题、链接、类别和计数需要的长度；`brief` 只出现在 `GET /blocked`。Layout 角标用这份瘦数据或计数，不为角标拉 brief。
- `GET /specs` 按 Serial ID 做 keyset 分页，只给需求列表。面包屑的 Spec 切换器改走已有 `GET /search`，不再把截断的列表当全量切换器。
- 阶段均值在有证据表明查询昂贵之前，不提前按完成事件做缓存表。
- SSE 的 `invalidate` 形状不变；断线后的轮询仍打这些查询。

**实施步骤。**

1. 留下当前 `/specs`、`/workbench`、`/blocked` 的查询计划、响应体积和页面耗时。
2. 拆工作台查询与全量 Spec 列表，瘦身 `waiting`，角标改走瘦数据。
3. 需求列表改 keyset 分页；面包屑改 `GET /search`。

**验收。** 数据量增加一个数量级时，工作台返回的数据量仍有上限；列表翻页无重复、无遗漏；面包屑不依赖全量 `/specs`；SSE 失效和断线轮询仍能得到正确结果。数据库查询计划与页面耗时在变更前后留档。

### 2.2 Run 日志增量解析与可见区域渲染（P0）

**状态。** 已实现（#188），随 PR #192 合并。

**现状。** [RunLog](../packages/web/src/RunLog.tsx)按 offset 拉取日志，但把新文本追加到 `position.text` 后，每次渲染都对全文执行 `groupLog`。`groupLog` 在 tool 完成时会改写更早的 block，思考过程在流式时也是暂态刷新，因此不能当成「只追加新 block」。页面挂载全部 block，没有可见区域窗口。服务端允许每个 Run attempt 最多 [50 MiB](../packages/api/src/logs/log-store.ts) 日志。页面不传 `?attempt=`：attempt 变了就清空从 0 重拉；CLI 才用 `--attempt`。

**建议。** 把 `groupLog` 收成持有 checkpoint 的增量解析（未完成行、未完成 thought、`call_id` 映射、before/after、key 计数）。输入新 chunk，输出新增或更新的 block；分段解析与全文解析结果必须一致。同一条 P0 做可见区域渲染，只挂当前窗口里的 block。保留「跟随最新」和「展开原始事件」。页面保持始终看最新 attempt，不加切换器。Web Worker 等 1/10/50 MiB 基线后再决定。

**实施步骤。**

1. 收集脱敏的 1/10/50 MiB 真实日志样本，记下当前打开时间、追加耗时和内存峰值。
2. 抽出可单测的增量解析，覆盖半行切片、中文跨字节边界、attempt 变化、tool 完成改写先前 block。
3. Run 页改为增量解析 + 可见区域渲染，跟随最新与原始事件语义不变。

**验收。** 分段解析结果与当前 `groupLog` 一致。记录 1/10/50 MiB 样本下的首次打开时间、追加 chunk 耗时和浏览器内存峰值，再决定是否需要 Web Worker。长日志下滚动到中部时，跟随已关闭，新 chunk 不把视口拽回底部。

### 2.3 收拢 worker 阶段模块接口（P2）

**现状。** [executor.ts](../packages/worker/src/executor.ts)同时负责 agent 修改、review、gate、merge、e2e、diagnose 及环境准备，文件已超过千行。现有测试覆盖较多，但新增执行器或阶段时容易跨多个流程修改。

**建议。** 在下一次扩展流水线时，先定义一个面向 worker 循环的阶段执行接口，例如「输入任务上下文与取消信号，返回阶段事实」。按阶段拆开实现，环境、日志、凭据和租约检查留在共同的内部模块。先迁一个阶段验证接口，再迁其余阶段；避免只为缩短文件而增加转发层。

**验收。** worker 循环调用方式保持稳定；新增阶段时不用修改已有阶段的内部逻辑；原有租约丢失、重试、门禁与合并测试继续通过。

### 2.4 迁服务器前明确身份与事件机制

**现状。** API 只监听本机且无登录，这是当前单人 PoC 的明确选择；[SSE 事件](../packages/api/src/events/hub.ts)只在单进程内传递。[总体设计](design.md)同时提到 M3 迁服务器、M5 登录权限，具体部署时点需要定稿。

**建议。** 在 M3 的部署方案中一次性决定：页面用户、CLI、worker 分别如何认证；worker 的租约凭证与仓库访问权限如何隔离；多 API 实例时事件如何跨实例投递；哪些状态变化必须保证最终可见。若 M3 仍保持单 API 实例，也应把这一限制写进部署约束，不提前引入事件总线。跨实例投递可以直接建在 2.6 的事件表上（Postgres `LISTEN/NOTIFY`）。

**验收。** 远程 worker 无法冒用其他 worker 的租约；未授权客户端不能读取 Run 日志或执行恢复动作；API 重启与 SSE 断线后，页面能通过现有轮询回退恢复正确状态。

### 2.5 后确认的需求拿不到名额就一直不开工（P0，缺陷）

**状态。** 已实现（PR #195）。

**现状。** 并发名额按整个项目算：`concurrencyInUse` 数的是项目里所有需求处于 queued、running 的票（[scheduler.ts](../packages/api/src/scheduling/scheduler.ts)）。名额释放时却只重排同一个需求：票 done 后 `finishTicket` 调 `schedulePass(本需求)`，票进 blocked 时 `blockTicket` 也一样（[results.ts](../packages/api/src/stages/results.ts)，那里的注释写的是「别的票可以开工了」）。确认时名额被别的需求占满的需求，之后不会再有事件给它排一次。

2026-11-06 在真 Postgres 上用一次性的 API 层测试复现：项目并发设为 1，需求 A、B 各一张独立的票，先确认 A，再确认 B（B 入队 0 张）。A 的票做完、A 进入收尾之后，B 仍是 running，票仍是 pending，B 的票一个作业都没有入队过。页面上 B 一直显示运行中；B 不是 paused，`plat spec resume` 用不上，只有往 B 里追加票这类会顺带调度 B 的操作能让它动起来。A 因为时长用完而暂停时也一样：A 的票跑完释放名额，`schedulePass(A)` 因为 A 不是 running 直接返回。M3 的验收「两个需求同时跑完」和多团队共用都会碰上。

**建议。**

- 名额释放之后（票 done、blocked、取消，需求取消；暂停的需求里还在跑的票结束时也算），对同项目里其他 running 的需求各跑一遍调度。注意加锁顺序：现在一律先锁需求再锁项目，不能在持有项目锁时去锁别的需求。可以在事务提交后逐个调用 `scheduleSpec`，或者改成以项目为单位的一次调度（全部改成先锁项目）。
- 加定时兜底：API 每隔一段时间对所有 running 的需求跑一遍调度，任何漏掉的触发都能自己恢复。
- 几个需求争名额时，按确认先后轮流分配，避免先确认的一直占满。
- 跨需求的分配规则写进 [总体设计](design.md) 的调度部分。

**实施步骤。**

1. 先把上面的复现写成回归测试（API 层，真 Postgres）。
2. 实现名额释放后的跨需求调度和定时兜底。
3. 实现轮流分配，补测试；更新设计文档。

**验收。** 回归测试通过：A 的票做完之后，B 的票随即入队；两个需求同时有可开工的票时，名额在两者之间轮流；只靠定时兜底时，B 也能在一个周期内开工。

### 2.6 状态变化和人的操作写进事件表（P1，度量的前提）

**状态。** 部分实现（M3：#215 事件表和失败来源、#216 人的操作、#227–#229 工期和度量页；ADR 0008 由数据库触发器写事件）。通知和 SSE 刷新仍由前后快照得出（见 4.13）；Finding 的「有用 / 没用」标记、PR 上的人工补提交和回滚检测还没有。

**现状。**

- 通知和页面刷新信号不是从状态变化本身来的：每个写操作前后各拍一次需求快照，比较差异得出（[announce.ts](../packages/api/src/events/announce.ts) 的 `aroundSpec`、`aroundTicket`、`aroundJob`）。快照在事务之外，每次七条查询，一次写操作多出十四条。按项目的作业更重：host-sync 在有 PR 开着时每分钟跑一次，它完成时会给项目里的每一个需求（包括早已合并的）各拍两次快照，再给每个需求各发一条 `invalidate`，需求越积越多，这笔开销跟着涨。两个 worker 几乎同时回报同一个需求时，后一个请求「之前」的快照可能早于前一个请求的提交，它的差异里就会再带上前一个的变化，同一条通知发两遍。
- 时间线是从 Run、PR、验收包和需求表拼出来的（[timeline.ts](../packages/api/src/tickets/timeline.ts)），人的操作不在里面。
- 平台不记录人做了什么：重试、改票、批准保护路径、放行、恢复都只改状态，不留「谁、何时、在页面还是 CLI」。review 意见（Finding）只有处理结果，没有人觉得它有没有用。PR 同步只记 head、状态、CI 和 review（[schema.ts](../packages/api/src/db/schema.ts) 的 `pull_requests`），不知道人有没有往 PR 上补提交，也不看 main 上有没有回滚。

平台方向讨论里提出的成功标准中，无人插手的比例、评审意见有用率、合并前要人补提交的比例、回滚率，现在都算不出来。

**建议。** 加一张只追加的事件表（时间、需求、票、Run、类型、来源：调度器 / worker / host-sync / 页面 / CLI、数据），和状态变化在同一个事务里写入；人的操作也写进去，登录之前先记来源和机器名。然后各处改从它读：

- 通知按游标消费事件，一个事件只发一次；
- SSE 的 `invalidate` 由事件产生，形状不变；
- 时间线直接读事件；
- 度量从事件算；
- 多个 API 实例时用 Postgres `LISTEN/NOTIFY` 分发，2.4 的跨实例投递就落在这里。

配套补三处数据：Finding 可以由人标「有用 / 没用」（页面先做，以后的评审机器人也用）；host-sync 记下 PR 合并时的 head 是不是平台最后推送的那个；main 上回滚了哪些带 `Ticket:` trailer 的提交。

**实施步骤。**

1. 建表；在调度、阶段结果、人的操作、收尾、PR 同步这些写入点，同一事务写事件（先和现有快照并行跑）。
2. 通知和 SSE 改从事件表消费，去掉前后快照。
3. 时间线改读事件；补 Finding 反馈、PR 补提交和回滚检测。
4. 按成功标准出第一版度量（先 SQL，后页面）。

**验收。** 两个 worker 同时回报同一个需求时，每条通知只发一次；任一张票能列出谁在什么时候做了什么；能算出一个需求里人插手的次数、平台 PR 的合并率和合并前补提交的比例；API 重启后通知从上次的游标接着发，不漏发。

### 2.7 调度按关键路径挑票（P2，和 2.5 一起做）

**现状。** 可开工的票按编号顺序挑（`schedulePass` 里 `ORDER BY id`）。默认每个项目、每个仓库同时都只跑 2 张，名额不够时，挡着一长串下游的票可能排在没有下游的票后面，整份需求的完成时间因此拉长。

**建议。** 按「这张票往下最长还有几张票」排序，相同再按编号；以后有了足够的阶段耗时数据，再按耗时加权。这仍然是由依赖边算出来的确定性规则，不交给模型（设计原则 1）。

**实施步骤。** 排序做成 shared 里的纯函数，单测覆盖链、扇出和契约边；`schedulePass` 按它的顺序挑票。

**验收。** 名额为 1 时，一条三张票的链的链头和两张独立的票同时可开工，链头先开工；在按固定阶段耗时模拟的测试里，同一份导入的总完成时间不比按编号排更长。

### 2.8 门禁提速：结果按代码树复用，依赖只装一次（P2，和 #159 一起）

**数据（2026-11-10）。** Mac 上的记录：门禁 67 次，每张票平均 2.1 次（票分支一次、合并候选一次）；最近一次门禁 16.7 秒里 setup（`pnpm install`）占 12.6 秒。试点仓库很小，换成 Java 这类仓库，两项收益都会更大。

> 进展（2026-11-10）：结果按「代码树 SHA + `gates.yaml` blob SHA」存进 `gate_results` 并复用，基线每次重新比较（`fix/gate-and-retry`）。依赖缓存还没做。
>
> 进展（2026-11-12）：门禁的依赖缓存先做了，不等 #159。S-33 的门禁 setup 每次 4 分 48 秒，几乎都在从公司 nexus 下载 431 个包（`reused 0`）。现在 worker 给每个仓库一个 `~/.afk/cache/deps/<仓库>/`，可写地挂进门禁沙箱的 `/deps-cache`，并把 pnpm（store 和元数据 `cache-dir`）、npm、Go、Gradle、pip 的下载目录指过去（其他工具用 `$AFK_DEPS_CACHE`）。Mac 上用沙箱镜像实测本仓库：空缓存 8 分 10 秒（431 个包全从 nexus 下）；第二次 10 秒，不下载任何包。元数据也得放进缓存：pnpm 12 安装前要按供应链策略核对 lockfile，每个包拉一次元数据，只缓存 store 时第二次照样卡在 nexus 上。核对结果有时效，过期后要联网重新核对，带着缓存的元数据约 12 秒；断网时会卡住，加 `prefer-offline` 也一样，所以没有加。agent 沙箱不挂。按仓库分而不按 lockfile 哈希分：这些缓存本身按内容寻址，同一仓库换了 lockfile 也能复用大部分。还没做：缓存只由 setup 写（门禁里的测试也能写到）、agent 沙箱只读挂载。

**现状。**

- 合并阶段总会在候选提交上整跑一遍门禁（[executor.ts](../packages/worker/src/executor.ts) 合并阶段的候选门禁）。票从开工到合并，集成分支如果没动过，候选的代码树和票分支上刚过门禁的那棵完全一样，配置和基线也一样，这一遍是重复的。门禁缓存按提交 SHA 记，而且只在 worker 进程的内存里（[gate.ts](../packages/pipeline/src/gate.ts) 的 `GateCache`）；候选是新的合并提交，永远命不中。
- 每次门禁都在全新沙箱里从头装依赖（本仓库是 `pnpm install --frozen-lockfile`，见 `.sandcastle/gates.yaml`）。Java、Go 这类仓库接进来之后，装依赖可能比跑测试还慢。

**建议。**

- 门禁结果按「代码树 SHA + 配置来源 SHA + 基线」复用，存进 `gate_results`（加一列树 SHA），worker 重启后也能复用。候选和票分支是同一棵树时直接用已有结果，GateResult 照常记下。设计原则 7 要求合并后再验证，验证的是合在一起的改动；树相同，就没有新的组合。
- 按「仓库 + lockfile 哈希」给门禁挂依赖缓存（pnpm store、`~/.m2`、Go 模块缓存等）。缓存只由门禁的 setup 写入，对 agent 的沙箱只读，免得一张票把缓存弄脏、影响别的票。和 #159（每个仓库用自己的镜像）一起设计：镜像管工具链，缓存管依赖。

**实施步骤。**

1. 先记基线：每张票的门禁次数，每次门禁里 setup 和各条命令的耗时。
2. 按树复用门禁结果，补测试（树相同复用；树不同、配置不同都照跑）。
3. 依赖缓存随 #159 落地。

**验收。** 集成分支没动过的票，合并阶段不再重跑门禁；同一个 lockfile 第二次跑门禁时 setup 明显变短；agent 写不进缓存。

### 2.9 agent 提供方做成项目配置（P1）

**现状。** 沙箱里的 agent 写死是 Cursor：[sandcastle.ts](../packages/pipeline/src/sandcastle.ts) 直接调 `cursor(...)`，skills 挂在 Cursor 的目录 `/home/agent/.cursor/skills`，镜像里也只装了 Cursor CLI。项目表上有 `default_agent`，`plat project create --default-agent` 也能写，但 worker 从不读它，填了也不起作用。Cursor 不报 token 用量，`runs.token_usage` 从来没有写入过。平台方向是外部模型不限、给多个团队用，各团队手里的模型和账号不一定相同。

**建议。** 让 `default_agent` 真正生效：提供方（Cursor、Claude Code、Codex 等，Sandcastle 都支持）和模型一起作为项目配置，以后可以按阶段覆盖（见 3.5）。随提供方变化的东西收在 pipeline 一处：怎么构造 agent、skills 挂在哪、需要哪个密钥、怎么取结构化输出和用量。Run 照常记下提供方和模型；能报用量的提供方把用量写进 `token_usage`。设计原则 5「按每次全新会话设计」不变。

**实施步骤。**

1. 在 pipeline 里抽出提供方描述，Cursor 是第一个实现，行为不变。
2. 加第二个提供方，用同一张演练票跑通整条流水线；镜像里装对应的 CLI（和 #159 的镜像分层一起考虑）。
3. `plat project create/edit` 和页面能显示、修改提供方；未知的提供方在登记时就拒绝。

**验收。** 同一张演练票分别用两个提供方跑完；Run 上能看到提供方和模型，能报用量的有用量；没配置的项目行为和现在一样。

## 3. 创新点子与验证方式

### 3.1 合并前风险预演

利用票依赖、模块重叠、分支头和门禁结果，给出「潜在冲突」「契约版本落后」「该仓库 PR 还在等待上游合并」等提示。每条提示必须附上可检查的事实和对应票、Run、分支链接；只做预警，不自动改写依赖图。总体设计已经把 trial-merge 与跨需求冲突列入 M3，此处建议先验证提示能否减少人工返工。

**小试验。** 在两个并行需求上记录平台提前提示的风险、实际发生的冲突与误报；误报过多则缩小规则，不扩大自动化权限。

### 3.2 验收差距视图

在现有验收包之上增加一个汇总：每项验收标准的状态、证据 Run、未验证原因、人工放行记录。优先显示未验证和被放行项，并保留按仓库查看。它是现有验收包的读法改进，不另造一份验收数据。

**小试验。** 让用户用该视图完成一次跨仓库验收，记录从打开交付页到完成决定的时间，以及是否仍需反复查日志或 PR。

### 3.3 处理建议的反馈闭环

对 blocked 原因码记录「推荐动作 → 人实际选择的动作 → 是否恢复 → 是否很快再次 blocked」。先做规则统计和人工可见的历史案例，不让模型直接决定重试或放行。M4 的追溯链路可为这项能力提供上下文。

**小试验。** 聚焦出现频率最高的两个 blocked 原因；只有当历史样本足够、建议明显优于当前固定文案时，再考虑更复杂的推荐方式。

### 3.4 用历史票回放评测

每条 Run 已经记下票的内容版本、基准提交、prompt、skills SHA、模型、Cursor CLI 版本、门禁结果和 review 意见。这就是一套现成的回归集，而且门禁是确定性的裁判，不需要人打分。升级 skills SHA、改覆盖层、升级 Cursor CLI、换模型或提供方之前，挑 10–20 张有代表性的历史票，从各自的基准提交重跑，比较一次通过门禁的比例、各种 fix 的次数、耗时、review 必须修改的条数和进 blocked 的原因。回放用单独的数据库（分支名带它自己的实例标识，不会和真实需求撞名），不开 PR；回放完取消这些需求，分支由清理作业删掉。

这样，操作手册「升级 skills SHA」一节就从人工核对覆盖层，变成看对比表做决定；信任阶梯的阈值、3.5 的策略表、给各团队推荐哪个模型，也都有了数据。成本是每张票几次 agent 运行，要计入预算。

**小试验。** 选 10 张已经 done 的票（单仓库、跨仓库、联调各有），用现在的配置回放两遍，先看结果本身的波动有多大；波动可以接受，再换一个模型对比。

### 3.5 失败后按策略升级模型

现在 fix 额度用完就叫人。可以用一张写死的策略表，在叫人之前再试一次更强的配置：比如 gate-fix 之后仍然失败，就换更强的模型或另一个提供方（2.9），按 `continue` 再跑一次；review 的 Standards 轴这类便宜的阶段用快模型。由表决定，不让模型自己决定（设计原则 1）；表里的取值来自 3.4 的回放结果。每次升级记成事件（2.6），度量里能看到升级后恢复的比例和多花的时长。

**小试验。** 用 3.4 里失败的票，比较「同一模型重试」和「换更强的模型重试」的恢复率；升级明显更好才上线。

### 3.6 确认前的拆票体检

无人值守能不能成，主要看票写得好不好；现在确认前只检查依赖图是否合法、模块是否重叠。可以在确认前预检里加几项确定性检查：每张票验收标准的条数和写法（能不能对应到测试）；模块 glob 在基准提交上匹配多少文件（太宽就提示拆）；是否碰到没有批准的保护路径；跨仓库时契约边是否齐全。再附上「历史上相似的票」（同一仓库、模块重叠）后来卡在了哪个原因码。只提示，不拦。

**小试验。** 拿已有需求的票离线跑一遍体检，看被标出来的票是不是正好是后来进 blocked 或 fix 次数多的那些；对得上才放进预检。

### 3.7 可点的验收：预览环境和 e2e 截图

最后一道人工检查是读验收包。联调环境已经能从各仓库的集成分支起一整套服务（compose），可以在需求进入 awaiting-review 时按需给人起一个预览环境（超时自动拆），验收包里给出地址；联调票的 e2e 用 Playwright 时，把截图和录屏存下来放进验收包，挂在对应的验收标准旁边。这是 3.2「验收差距视图」的延伸：差距视图告诉人哪些还没验证，预览环境让人自己点一下。平台部署到服务器之后，预览环境的访问控制归 2.4。

**小试验。** 在下一个跨仓库需求上手动起一次预览环境，记录从打开交付页到做出合并决定的时间，和只看验收包时比较。

### 3.8 规范回流：反复出现的问题变成规范

同一类问题会在不同的票上反复出现：同一条 lint 规则导致的门禁失败、Standards 轴反复提的同一种意见、人在 Retry note 里一再交代的同一件事。可以在每个需求收尾后按仓库汇总，生成一份「改进 AGENTS.md 或门禁」的建议；人同意后，作为一个 improvement 类型的需求走同一条流水线。它和 3.3 不同：3.3 改进的是人怎么处理卡住的票，这一条改进的是 agent 的输入，让同样的错少犯。

**小试验。** 先手工汇总已有需求的 Finding 和 Retry note，看能不能找出 2–3 条值得写进 AGENTS.md 的规则；写进去以后，看后续需求里同类意见有没有减少。

## 4. 第三轮：按四个目标复查（2026-11-10）

M3 合入 main（PR #237）之后，按四个目标复查：

- **配置**：用平台的人配置起来顺手、简单；
- **效果**：平台做出来的东西和手动用 matt skills 一样好，或者更好；
- **缺陷**：功能上没有明显的逻辑漏洞；
- **性能**：还能再省的地方。

读了流水线的提示词和覆盖层、阶段流转、调度、worker 执行、托管同步和通知，并在用户 Mac 上的平台库里只读统计了真实记录（2026-10-29 至 11-10：16 个需求、35 张票、204 次 Run）。下面的数字都出自这批记录：

| ---------------------------- | ------------------------------------------------------------------------------------------------------ |

| 需求级 final-review 的 Spec 轴 | 11 次，在 S-11、S-15 抓到 4 条必须修，引用的都是需求的 User Story                                     |
| Standards 轴（票级 + 需求级） | 29 次，必须修 0 条，建议 90 条                                                                         |

样本小，用来定方向，不当基线。

### 4.1 门禁命令从 run.json 读，提示词不写死 npm（效果，P0）

**现状。** 七个会改代码的阶段提示词（implement、integration-implement、gate-fix、review-fix、merge-fix、final-fix、update-branch，在 [prompts](../packages/pipeline/prompts/) 下）都写着「`npm run typecheck` 和 `npm test` 都要通过，再提交」。门禁真正跑的命令在各仓库的 `.sandcastle/gates.yaml` 里，[context.ts](../packages/pipeline/src/context.ts) 生成的 `/context/run.json` 不带它们。现在的试点仓库都是 Node，碰巧对得上；平台要给语言不限的几个团队用，到了 Java、Go、Python 仓库，agent 会去跑一条不存在的命令，要么自己猜，要么提交前的自检落空，门禁失败后多一轮 gate-fix。

**建议。** worker 渲染上下文时，把这个仓库这次生效的门禁命令（带名字，`setup` 单列）写进 `run.json` 的 `gate`。提示词改成「提交前按 `/context/run.json` 的 `gate` 逐条跑通」。matt 的 implement 原文要求「经常跑类型检查和单个测试文件，最后跑一次全量」：覆盖层补一句，单个测试文件怎么跑看仓库的 `AGENTS.md`，afk-setup 写 `AGENTS.md` 时把这一条写进去。

**验收。** `gates.yaml` 用 `make test` 的仓库，提示词和 `run.json` 里没有 npm；加一条测试，扫 prompts 目录，不允许写死具体的构建或测试命令。

### 4.2 Standards 轴按 skill 原文找全规范文档（效果，P1）

**现状。** [review-standards.md](../packages/pipeline/prompts/review-standards.md) 替 agent 做完了 code-review 第 3 步，把标准来源定成「`AGENTS.md` + 覆盖层的规范 + 坏味道基线」。matt 原文第 3 步要求搜全仓库里所有写了代码规范的文件，`CODING_STANDARDS.md`、`CONTRIBUTING.md` 存在时必须在列。其他团队的规范多半写在 `CONTRIBUTING.md`、`docs/` 或 lint 配置的说明里，不在 `AGENTS.md`。29 次 Standards 轴审查，必须修是 0 条。

**建议。** 第 3 步交还给 agent：提示词改成「按 skill 第 3 步找标准来源，`AGENTS.md` 和覆盖层写明的规范一定在列」，结果里加 `sources`（用到的文件），记在 Run 上，验收包里能看到这次审查依据了哪些规范。afk-setup 写 `AGENTS.md` 时，把仓库里已有的规范文档列进去，作为兜底。

**验收。** 一条硬规范只写在 `CONTRIBUTING.md` 里的仓库，违反它的改动被 Standards 轴判为必须修，`sources` 里有 `CONTRIBUTING.md`。

### 4.3 票级 Spec 轴也对照这张票负责的 User Story（效果，P1）

**现状。** 票级 Spec 轴只对照票的 `What to build` 和验收标准；[review-spec.md](../packages/pipeline/prompts/review-spec.md) 明说 `/context/spec.md` 「只是背景，不是审查的对照物」。拆票时没写进验收标准的细节，票级审查看不见，要到需求级 final-review 才被抓到：S-11 的「列表仍用整串精确匹配，未替换已有 stub」、S-15 的「发货后的列表重载不带当前关键词」，引用的都是需求的 User Story。到了 final-review 才修，是一次 final-fix 对着整个需求的改动修，比在票里修上下文更大，也更晚。手动用 matt skills 时，审查的人手里有整份 spec。

**建议。** 让每张票写明它负责哪几条 User Story：在 tracker doc 里给 to-tickets 加一个 front matter 字段（例如 `stories: [1, 4]`，和 `repo:`、`modules:` 一样由平台约定，skill 原文不改），导入时检查编号在需求里存在。票级 Spec 轴的对照物加上这几条的原文。没写的票照旧。和 3.6「确认前的拆票体检」配合：体检提示「这几条 User Story 没有任何票负责」。

**验收。** 用 S-11、S-15 的票做回放（3.4）：上面两条至少一条在票级就被判为必须修；没写 `stories` 的票，审查行为不变。

### 4.4 审查建议：可开关的整理步骤（效果，P2）

**现状。** 113 条审查建议全部只进了验收包，没有一条被处理。matt 的 tdd 原文说「重构不在红 → 绿循环里，属于 review 阶段」；平台照原文不在循环里重构，但 review 阶段只修必须修，坏味道全部只记不改（ADR 0002：「AFK 运行里不做重构」）。手动用时，人看完 code-review 通常会让 agent 顺手整理；平台少了这一步，几十条建议也很难指望人在验收时逐条看。

**建议。** 加一个项目级开关，默认关，先在平台自己的仓库试。开启时，review 之后如果 Standards 轴有建议，跑一次整理阶段：只做不改行为的整理，只挑改动小、局部的建议（命名、同一文件里的重复、过长的函数），改完照常过门禁；门禁不过就丢掉这次整理、按原样合并，不进待处理，也不占 fix 额度。被处理的建议记为 `refactored`。这改变了 ADR 0002 的结论，先写一条新 ADR。

**验收。** 开关关着时行为不变；开着时整理失败不影响票完成；验收包标明哪些建议已被整理。用 3.4 的回放比较开关前后 final-review 的建议数，以及人在 PR 上补提交的比例。

### 4.5 final-fix 修完的问题标为已修复（缺陷，P0）

**现状。** [results.ts](../packages/api/src/stages/results.ts) 只在票级 review-fix 完成时，把这张票审查里的必须修标为 `fixed`。需求级 final-fix 完成后，final-review 的必须修仍是 `unhandled`。S-11、S-15 的 4 条都是这样：问题已经修好、合并了，PR 描述里的验收包仍写着 `[unhandled] … must-fix`，看的人会以为有问题漏了；按 Finding 算的度量也会偏。

**建议。** final-fix 完成时，把同一需求、同一仓库这次收尾的 final-review 里未处理的必须修标为 `fixed`。补一条迁移，纠正已有数据（final-fix 结果为 done 的，之前那次 final-review 的必须修）。

**验收。** API 层测试：final-review 给出 fix → final-fix done → 验收包和 PR 描述里这几条是 `[fixed]`。

### 4.6 push 失败先原地重试，重派时不再重跑 agent（缺陷，P0）

**现状。** agent 做完以后，worker 取回提交、打 trailer、做 pre-push 租约检查，然后只 push 一次；失败就作为基础设施失败让作业失败、重派（[executor.ts](../packages/worker/src/executor.ts) 的 `agentChange`）。提交其实还留在 worker 主克隆的分支上，重派后会带进新 slot，但 agent 照样从头跑一整轮。T-32 的 implement 两次都在最后 push 时 `Failed to connect to github.com:443`，前两次分别跑了 28、32 分钟，第三次才成功：网络抖一下，就白花约一小时 agent 时间，还占着名额和预算；连着三次就进待处理。

**建议。**

1. push 遇到网络类错误（连不上、超时、5xx）原地退避重试，例如等 10、30、90 秒，每次重试前再做一次 pre-push 租约检查；被拒（non-fast-forward、保护分支、无权限）不重试。
2. 第二步（可后做）：仍然失败时，把这次 agent 的结构化结果随作业失败一起交给 API 存下；重派的作业看到分支上已有这次 Run 的提交和结果，跳过 agent，直接 push。

**验收。** 假远端前两次连接失败、第三次成功：作业一次完成，agent 只跑一次；被拒的 push 不重试。

### 4.7 不可恢复的 agent 错误不重试（缺陷，P1）

> 进展（2026-11-11）：密钥失效和额度用完这两类改为暂停所有 agent 作业、作业回到队列、页面「恢复」继续（`fix/gate-and-retry`）；模型名无效、联调镜像构建失败仍是第一次就 blocked。

**现状。** 一次收尾里的 final-review 连续三次在一分钟内失败，错误都是 `ActionRequiredError: Unauthorized request`。作业失败一律重排，到第三次（`MAX_JOB_FAILURES`）才进待处理，三次错误一模一样。联调服务的镜像构建失败也是同样，三次都在十几秒内失败。

**建议。** worker 把能确定不是偶发的错误单独归类：Cursor 鉴权失败、模型名无效、额度用完、联调镜像构建失败。这类错误第一次就让作业失败、不再重排，原因写成人能看懂的一句，例如「Cursor 密钥失效或没有权限，更新 `~/.afk/env` 里的 `CURSOR_API_KEY` 后重试」，失败来源记为外部服务。可选：密钥问题出现后，worker 暂停领取 agent 作业，在工作台状态区提示，免得每张票都撞一遍。

**验收。** 假 agent 返回鉴权错误：作业失败一次就进待处理，简报给出上面那句话。

### 4.8 合并中的票也占并发名额（缺陷，P2）

**现状。** 并发名额只数 queued、running 的票（[scheduler.ts](../packages/api/src/scheduling/scheduler.ts) 的 `concurrencyInUse`）。票在 merging 状态时仍在跑合并候选的门禁、联调票的 e2e 环境，失败后还会跑 diagnose agent，这些都不占名额，所以项目的实际并发比设的上限高。现在由 worker 的 slot 数兜住总量；多个团队共用 worker 以后，一个项目合并中的票会挤占别的项目的 slot。

**建议。** merging 的票也计入名额；设计文档里写清楚项目并发和 worker slot 各管什么。

**验收。** 并发设为 1 时，一张票在合并期间，同项目的下一张票不开工。

### 4.9 `--default-agent` 在 2.9 之前先拒绝（缺陷，P2）

**现状。** 2.9 已经记过：`plat project create/edit --default-agent` 能写，worker 不读。M3 之后仍是这样，填了的人会以为它生效了。

**建议。** 2.9 落地之前，登记时拒绝 `cursor` 以外的值，并说明目前只支持 Cursor。

**验收。** `--default-agent claude-code` 被拒，并给出原因。

### 4.10 afk-setup 不要求 GitLab 用户登录 gh（配置，P0）

**现状。** [afk-setup](../skills/afk-setup/SKILL.md) 第 1 节把 `gh auth status` 已登录列为前提，缺了就停下；第 4 节第 3 步用 `gh label` 建 triage 标签。M3 的目标是公司 GitLab，纯 GitLab 团队在第一步就被拦住。需求和票现在都在平台里，GitHub 上的标签也用不到。

**建议。** 只有项目里有 GitHub 仓库时，`gh` 才是前提。确认没有 skill 还会用 GitHub 标签后，删掉建标签这一步。再把 afk-setup、tracker doc 模板和 `plat init` 里只适用于 GitHub 的步骤排查一遍。

**验收。** 一台没装 gh 的机器，对 GitLab 项目跑 `/afk-setup` 能走完。

### 4.11 `scripts/up.sh` 认 GitLab 令牌（配置，P0）

**现状。** [up.sh](../scripts/up.sh) 会检查并帮着保存模型和 Cursor 密钥，代码托管只查 GitHub App。GitLab 令牌（`~/.afk/secrets/gitlab/<host>`，权限 600）它既不检查也不帮着写；GitLab 用户启动时反而看到「No GitHub App credentials」的警告。令牌权限不对，要到 worker 第一次跑托管作业才报错。

**建议。** 托管凭据改成「至少有一种」。有 GitLab 令牌文件，就逐个检查权限，并调用 `GET /api/v4/user` 验证，显示用户名和到期日（复用 #221 的自检）。一种都没有时，在终端里问用 GitHub 还是 GitLab；选 GitLab 就问主机和令牌，写文件、设 600、验证。GitHub App 只在选 GitHub 时提示。

**验收。** 只有 GitLab 令牌的机器，`up.sh --check` 全部通过，没有 GitHub 的警告；令牌文件权限是 644 时，给出 `chmod 600` 的命令。

### 4.12 项目设置能在页面上看和改（配置，P2）

**现状。** 模型、并发、时长和预算上限、保护路径、契约路径，只能用 `plat project edit` 和 `plat repo edit` 改；页面上没有写入口。其他团队的负责人不一定守在规划机器前。

**建议。** 项目页加「设置」：列出全部生效值和来源（项目设置还是平台默认），能改的用表单调同一个接口；修改记成人的操作事件（#216）。登录（M4）之前只在本机页面开放。

**验收。** 在页面上改并发上限，下一次调度就按新值；事件表里有这次修改。

### 4.13 托管同步只看没结束的需求，没变化不推刷新（性能，P1）

**现状。** host-sync 每个项目每分钟一次。worker 领取它、交回结果时，API 都给作业涉及的需求拍前后快照（领取在 [worker-routes.ts](../packages/api/src/http/worker-routes.ts)，交回在 [announce.ts](../packages/api/src/events/announce.ts) 的 `aroundJob`）。项目级作业涉及的是项目里**所有**需求，包括早已合并和取消的。每次快照约 10 条查询，其中两条按 JSON 字段扫整张 jobs 表，所以一个项目每分钟大约是「4 × 需求数 × 10」条查询。交回后还给每个需求各推一条 `invalidate`，不管有没有变化，每个打开的页面因此每分钟都重拉工作台、待处理、需求列表和项目。这些开销都随历史需求数线性增长。2.6 的「通知改从事件表发」只做了一半：事件表有了，通知和刷新仍由前后快照得出。

**建议。** 先做轻的一步：项目级作业只对没结束的需求（有开着的 PR，或还没到终态）拍快照；前后快照相同的需求不推 `invalidate`。再按 2.6，把通知和 SSE 改成按游标消费事件表，去掉前后快照。

**验收。** 一个有 50 个已合并需求、1 个开着 PR 的项目：一次 host-sync 的查询数不随已合并需求增长；PR 没有变化时，页面收不到 `invalidate`。

### 4.14 运行中的需求不每次跟进默认分支（性能，P1）

**现状。** 默认分支每前进一次，每个 running 的需求都会在相关仓库排一个 update-branch（[update-branch.ts](../packages/api/src/host/update-branch.ts)）：合并默认分支，在候选上整跑一遍门禁，并和这个需求的票合并共用一把锁。还在排队的会合并成一个，但正在跑的时候默认分支又前进，就再排一个。几个团队共用的繁忙仓库一天合几十个 MR，一个跑几小时的需求就要跑几十次门禁，这期间票的合并都在等。

**建议。** running 的需求不再每次都跟进，只在三种情况更新：(a) 用 trial-merge 那样的 merge-tree 检查，发现和默认分支会冲突（不跑门禁，很便宜）；(b) 进入收尾前（现在已经有）；(c) 落后超过 N 个提交或 T 小时（项目设置）。awaiting-review 之后的规则不变。

**验收。** 默认分支前进 10 次、和需求没有冲突时，运行期间 update-branch 至多一次（由落后阈值触发）；有冲突时照现在的流程走。

### 4.15 票级审查的成本（性能，P2）

> 进展（2026-11-12）：4.2、4.3 上线后的数据见第 7 节，结论和建议并入 7.2，本条不再单独做。

**现状。** 票级审查 50 次，花了 227 分钟 agent 时间，没有产出一条必须修；需求级 final-review 还会按仓库把整份改动再审一遍。

**建议。** 先做 4.2、4.3，让票级审查真正有用，然后用 3.4 回放看数据。如果票级 Standards 轴仍然几乎只给建议，就换成快模型（3.5 的策略表），或者 Standards 只在需求级审。Spec 轴留在票级：越早发现越便宜。

**验收。** 回放比较改动前后：票级必须修条数、final-review 必须修条数、审查总时长。

### 4.16 测试在 Mac 上也能全绿（开发效率，P1）

**现状。** 2026-11-10 在两台机器上跑全量 `pnpm check`，typecheck 和 lint 都通过，测试都不是全绿，原因都在测试环境：

- **Linux 沙箱**（磁盘剩 4.2 GiB）：worker 相关测试成片失败。剩余空间低于停领阈值 5 GiB（[disk.ts](../packages/api/src/disk.ts)），测试没有注入磁盘余量，API 就不发作业；机器慢时，不少测试还超过默认的 5 秒超时。调低阈值、放宽超时后全部通过。
- **Mac**（228 秒）：1941 个测试过了 1871 个，失败 70 个。门禁和 e2e 的测试在宿主机上执行 `timeout N sh -c …`，Mac 没有 GNU `timeout`（退出码 127）；两个沙箱清理测试的临时目录在 `/var`，那是 `/private/var` 的软链，测试里假 docker 报的路径没有解析软链。这些文件拿回 Linux 复跑，全部通过。

平台的 API 和 worker 都跑在 Mac 上，在 Mac 上验证最接近真实情况，Mac 也比沙箱快得多。

**建议。**

1. 测试注入磁盘余量（`freeBytes`），不读宿主机。
2. 门禁和 e2e 的超时不依赖宿主机的 `timeout`：真沙箱里照旧，测试用的假沙箱改用 Node 计时、超时杀进程。
3. 沙箱清理测试先对临时目录 `realpath`。
4. 用真 git 和 HTTP 的端到端测试设更长的超时。

**验收。** Mac 上 `pnpm check` 全绿；沙箱磁盘低于 5 GiB 时，测试结果不变。

### 5.1 票分支以 origin 为准，推送带租约（缺陷，P0）

**现状。** T-58 的经过：

1. 21:49 合并冲突，平台派出 merge-fix。21:52 用户手动往 `agent/ba6752/T-58` 推了一个提交（8ee39a2，修测试收尾）。
2. merge-fix 跑完 10 分钟后推送，被拒（`fetch first`）。之后 merge-fix 和 implement 又跑了 8 次，每次跑 7–17 分钟，推送都被拒（`non-fast-forward`）。每三次进一次待处理，用户重试了三次，期间又手动推了两次（22:35、23:57）。
3. 23:09 和 23:57 两次重试从门禁接着跑，门禁、审查和最后的合并用的都是 worker 本地的提交（ceccbc6、6d412e4），这两个提交从没推上过票分支。

原因有四处，main 上都还在：

- **本地分支卡在旧提交上。** worker 主克隆跟进 `agent/*` 时不带 `+`，注释写着「拒绝更新也没关系」（[repos.ts](../packages/worker/src/repos.ts) 的 `ensure`）。设计的前提是票分支只有平台在写；有人推过之后两边分叉，本地就一直停在自己那条线上。之后每次运行都从这里起步，推送必然被拒。agent 跑完后取回的提交也先写进本地分支，再推送；推送失败了，本地分叉得更远。
- **被拒当成平台故障重试。** 推送被拒属于确定性失败，却记成 `job-failed`、失败来源 platform，按 `MAX_JOB_FAILURES` 原样重排三次。4.6 只让网络错误在原地重试、被拒不重试，作业级的重排没管。而且要等 agent 跑完才推送，所以每次都白花一整轮 agent 时间才发现。推送前的 `prePush` 只检查租约，不看远端分支。
- **改写了别人的提交。** merge-fix 的 agent 自己把远端分支合了进来，`stampTrailers` 从本地 tip 起算，把用户推的提交也打上 trailer、改写了一遍。T-58 合进集成分支时有 24 个提交，用户那条线是 17 个；「Make test HTTP shutdown reliable」出现了两次（3f9f623、75191c4）。
- **验过的提交不在分支上。** gate 和 merge 只看主克隆的本地 ref，不核对远端。这次 6d412e4 和用户最后推的 f3f1515 代码树完全一样，所以没出事；换一次，平台合进集成分支的就可能是没人见过的代码。

**建议。**

1. **远端是唯一的事实。** 每个阶段在用票分支之前，先 `ls-remote` 看远端 tip：远端领先，快进本地；本地领先（之前取回了、没推上的工作），先推上去；两边分叉，以远端为准，本地那条另存为 `refs/afk/orphan/<run>` 留证，记一条事件。`ensure` 不再静默放过分叉。
2. **推送一律带租约。** 票分支也用 `--force-with-lease=<ref>:<本轮起点>`。这样被拒只剩一种意思：运行期间有人推了。记为新的失败原因（例如 `branch-moved`），不自动重排：推的人是人，按 5.2 当作人接手；推的人是平台自己（不该发生），进待处理并把两条线都写进简报。
3. **先查后跑。** 派 agent 之前，以及 `prePush` 时，都比一次远端 tip 和本轮起点，不一致就立刻停下，不要等 agent 跑完。
4. **只给本轮自己的提交打 trailer。** `stampFrom` 从本轮起点和远端 tip 里更新的那个算起，远端已有的提交一律不改写。
5. **验的就是分支上的。** gate、review、merge 开始前断言本地 tip 等于远端 tip，不等就按第 1 条处理，再从头验。
6. **确定性的推送错误不重排。** non-fast-forward、保护分支、无权限，第一次就进待处理，和 4.7 同一套归类。

**验收。** 用假远端写测试，票的流水线和需求收尾（final-fix、update-branch）两条路都要覆盖：

- agent 运行期间远端被推了一个提交：推送失败一次就停，不重排，agent 只跑一次。
- 主克隆的票分支和远端分叉：下一个阶段从远端 tip 起步；本地那条留在 `refs/afk/orphan/`。
- 远端已有、不是本轮做的提交：推送后提交 SHA 不变，不出现重复提交。
- 本地 tip 和远端不一致时：gate 不在本地 tip 上跑。

### 5.2 人接手票分支：先暂停，交回后从门禁接着跑（体验，P1）

**现状。** 人想自己修一张票，只能直接往票分支推。平台不知道，照样派作业，两边同时写一条分支，就是 5.1 的局面。用户在重试备注里写了「merged integration, links migration 0064, push after rebase」，平台不读这句话，照常从 implement 跑起。

**建议。**

1. `plat ticket takeover T-58`（页面上同一个按钮）：取消这张票正在跑的作业，票进入「人接手」状态，调度不再派它的作业。
2. `plat ticket handback T-58`：平台取票分支的远端 tip，从门禁接着跑（`resumeStage = gate`），人推的提交照原样保留。
3. 兜底：托管同步每分钟轮询时，发现 `agent/*` 上有不是平台 bot 推的提交，就自动暂停这张票，记事件，发通知（M4 的飞书）。5.1 第 2 条遇到人推的情况，也走这条路。

**验收。** 接手期间票不会被派作业；交回后第一个 Run 是 gate，`base`/`head` 是人推的提交；没执行接手就直接推送的，下一次轮询后票被暂停，待处理里写明是谁推的。

### 5.3 `worker-demo` 测试收尾不稳定（开发效率，P0）

**现状。** 三次门禁失败都出在测试收尾：

- run 364（T-58 第一次门禁）：`planning-docs-api.test.ts` 和 `worker-demo.test.ts` 的 afterEach 超过 20 秒，下一个测试跟着失败。gate-fix 改成先 `DROP DATABASE … WITH (FORCE)`、再关连接池，还会强制关掉剩下的 HTTP 连接（bf70b85，就是现在的 [test-db.ts](../packages/api/src/db/test-db.ts)）。
- run 375（同一个提交 bf70b85）失败，21:34 重跑同一个提交（run 390）通过。报错是 `terminating connection due to administrator command`（57P01），堆栈在 heartbeat 路由里。
- 用户 21:52 推了 8ee39a2 再修一次。00:30 T-61 的门禁（run 424，已经含这个修复）又是同样的 57P01。

推测：测试结束时，测试里的 worker 循环还在以 50 毫秒的间隔发心跳。`listen().close()`（[fake-worker.ts](../packages/api/src/test/fake-worker.ts)）用 `closeAllConnections` 掐断了 socket，但正在执行的路由处理还在查库；这时强制删库，查询抛出 57P01。`ignoreForcedDrop` 只挂在连接池的 `error` 事件上，管不到路由里的查询，错误成了未处理异常，vitest 判整轮失败。

**建议。** afterEach 按顺序收：先停掉测试里的 worker 循环并等它退出，再等正在执行的请求处理完、关 HTTP 服务，然后 `pool.end()`，最后删库。先在 Mac 上复现，确认原因再改。

**验收。** Mac 上把 `worker-demo.test.ts` 和 `planning-docs-api.test.ts` 各连跑 50 次，一次都不失败；全量 `pnpm test` 连跑 5 次全绿。

### 5.4 门禁失败先在同一提交上重跑失败的测试（效果，P1）

**现状。** 门禁一失败，就派 gate-fix；gate-fix 用完还失败，就进待处理。测试不稳定时，gate-fix 修的是不存在的问题：T-58 花了 23 分钟，T-61 花了 16 分钟，T-58 还卡住等人 46 分钟。其他团队的仓库也会有不稳定的测试，平台不能指望每个仓库都先修干净。

**建议。**

1. 门禁里只有测试失败时，在同一提交上只重跑失败的测试文件一次（JUnit 里有文件名；`gates.yaml` 里给测试命令加一个可选的「只跑这些文件」模板，没配就整条重跑一次）。
2. 重跑通过：门禁算通过，记一条 Finding（不稳定测试，带测试名），票照常往下走，不占 gate-fix 额度。重跑仍失败：照现在的流程派 gate-fix。
3. 用 `gate_results.test_cases` 按测试名统计「同一代码树先失败后通过」的次数，在项目页列出不稳定测试，验收包里也写上。

这和 1.5「能自己恢复的失败先自动重试一次」是一回事，落在门禁上。

**验收。** 假门禁第一次让一个测试失败、重跑通过：票不派 gate-fix，Finding 里有这个测试名。两次都失败：派 gate-fix，行为和现在一样。

### 5.5 生成文件的冲突交给再生成命令，不叫 agent（性能，P1）

**现状。** 并行的两张票都改了表结构，就会各自生成编号相同的迁移，合并时 `_journal.json` 一定冲突。T-58 的迁移因此两次改号（0064 → 0065）。生成的 `openapi.json`、`schema.d.ts` 也会冲突（T-61）。每次冲突都要一次 merge-fix（约 10 分钟 agent），外加重跑门禁 5–9 分钟。

**建议。**

1. **平台通用。** `gates.yaml` 可以声明生成文件和再生成命令，例如 `generated: [{ paths: [...], run: "pnpm gen:api" }]`。合并冲突只落在这些文件上时，merge 阶段在沙箱里取集成分支的版本，跑命令，提交，然后照常跑合并后的门禁，不派 merge-fix。冲突里有别的文件，还是派 merge-fix，并把这些命令写进它的上下文。
2. **本仓库。** `openapi.json`、`schema.d.ts` 用 `pnpm gen:api` 再生成。迁移不能直接重跑 `db:generate`，因为 0035 这类手写的触发器 SQL 会丢。写一个确定性的 `scripts/rebase-migrations.sh`：把本票新增的迁移改号排到集成分支最新编号之后，同步改 `_journal.json` 和 snapshot 的 `prevId`。
3. `.sandcastle/gates.yaml` 是保护路径，第 2 条的配置由人来改。

**验收。** 两张票各加一个迁移、并行合并：第二张不派 merge-fix，迁移编号连续，合并后的门禁通过；冲突里还有普通源文件时，照常派 merge-fix。

## 6. 第五轮：agent 自己做的决定（2026-11-12）

这一轮只看一件事：需求确认后，worker 派出的 agent 遇到开发中的问题时怎么处理。为了做到 AFK，[覆盖层](../packages/pipeline/prompts/overlay.md) 规定没有人回答：「能撤回的小事」自己决定，写进结构化输出的 `uncertainties`；「必须由人决定的事」（契约要改、验收标准互相矛盾、缺必需的东西）输出 `cannot-proceed`。问题在于：模型自己做了多少决定、这些决定之后有没有人看。

数据出自 Mac 上平台库的只读查询（S-1…S-28，444 次 Run）。`uncertainties` 约 200 条，人工逐条读过，下文引用的都带 Run 号，可以回查：

| 观察 | 数字 |
| --- | --- |
| 会改代码的阶段写下的 `uncertainties` | implement 67 次 Run 里 59 次写了，共 176 条；gate-fix、merge-fix、final-fix、update-branch 另有 26 条 |
| agent 停下交给人（`cannot-proceed`） | 2 次（一次是要改 `.github/**`，一次是门禁的 setup 连不上 npm） |
| 票级审查 | 116 次，必须修 0 条；其中 Spec 轴 50 次，必须修 0、建议 0 |
| 需求级 final-review 的 Spec 轴 | 17 次，必须修 4 条 |
| 审查建议 | 279 条，全部只进了验收包 |

结论：现在的实现把 AFK 做成了「不问」，而它应该是「不等」。agent 遇到的问题全部变成它自己的决定，写成一段自由文本；这段文本在开 PR 之前没有任何环节会读，票级审查又从没拦下过东西，所以这些决定实际上没人复核。

> 2026-11-12 重新 grill 后的结论见 [ADR 0010](adr/0010-afk-means-do-not-wait.md) 和 spec #262，下面各项已按结论改写。和第一稿的主要差别：不新增待处理类别，开 PR 前也不叫人；`needs-human` 和没做掉的 `deferred` 在开 PR 时列在验收包最前面，由合并人定。只有删测试（6.6）和 Recheck 不过（6.3）会中途叫人。

### 6.1 决定带类型，平台按类型处理（效果，P0）

**现状。** 176 条决定对 2 次停下。按覆盖层的规则，下面这些本该交给人，模型都自己定了，然后继续：

- **实现和契约对不上。** Run 13：409 没写进 OpenAPI，「不改契约，直接实现」；Run 14：响应多了 `byStatus`，契约没写，靠「契约允许多余字段」放过；Run 70：写了「契约里的 customer/status/sort 需另开契约票」，这张票从没建出来。
- **票、需求和现有代码互相矛盾。** Run 159、177：契约写「去掉首尾空白」，现有 PATCH 校验不去，选了现有代码；Run 171：票的验收标准和 User Story 6 写法不同，选了 User Story。
- **票的约束和 TDD 冲突。** Run 31、47、53、54、75：票写「只改这个文件、不改别的」，按红 → 绿照样加了测试文件。

原因是两条路的代价不对称：`cannot-proceed` 让票进待处理、叫人回来，在页面上看起来是失败；继续做没有任何代价。agent 的理性选择就是永远继续。覆盖层对「小事」和「必须由人决定的事」只给了原则，没有例子，「契约没写这个状态码」被当成了小事。

**建议。**

1. 结构化输出里用 `decisions` 取代自由文本的 `uncertainties`，每条是 `{ kind, text, ref? }`：
   - `choice`：命名、次要取舍，可以撤回；
   - `conflict`：票、需求、契约、现有代码之间对不上，选了其中一边；
   - `known-gap`：知道没做、或做了但有问题的地方；
   - `deferred`：留给别的票（`ref` 写票的显示编号，没有现成的票写 `new`），见 6.5；
   - `workaround`：绕过仓库或环境的问题，见 6.7。
   过渡期仍接受字符串数组，记成 `choice`。
2. 覆盖层补例子：契约没写的状态码、字段、校验规则，票和 User Story 写法不同，票的约束和 tdd 冲突，都是 `conflict`，不是小事。仍然继续做，但要记成 `conflict`，写清楚两边原文和选了哪边。`cannot-proceed` 只留给三种情况：缺做下去必需的东西、要改没批准的保护路径、契约非改不可。
3. 平台按类型处理，**不阻塞流水线、不叫人**：决定不进待处理队列，也不发通知；`conflict` 和 `known-gap` 由 Spec 轴下结论（6.2），`deferred` 在收尾核对（6.5）。
4. 所有会改代码的阶段都写 `decisions`，联调 implement 也写。页面、验收包、PR 描述和 `plat` 把「模型不确定的地方」改叫「决定」：`conflict`、`known-gap` 逐条列出，`choice`、`workaround` 只给条数。

这改变了「agent 不提问」的含义：仍然不停下等人，但问题要交出来（[ADR 0010](adr/0010-afk-means-do-not-wait.md)）。

**验收。** implement 的结果里有一条 `conflict`：票照常进门禁，待处理队列里没有它，验收包的「决定」里有它。旧格式的字符串数组仍然有效，记成 `choice`。

### 6.2 审查对实现者的决定逐条下结论（效果，P0）

**现状。** 票级审查 116 次，必须修 0 条；同期需求级抓到 4 条。最清楚的一例是 S-15：T-25 的 implement（Run 111）自己写了「批量发货成功后的列表重载仍不带当前 note 条件；票未要求，搜索态下发货可能看到未过滤列表」，票级审查没拦，到需求级 final-review 才被判必须修，再用 final-fix 去修。信息在 implement 时就有，只是审查看不到：[review-spec.md](../packages/pipeline/prompts/review-spec.md) 只给票、契约和 User Story，不给实现者的决定。4.3 让 Spec 轴看到了这张票负责的 User Story，但模型的取舍恰恰都落在验收标准和 User Story 没写到的地方。

**建议。** 审查运行的 `/context` 加上这张票之前各阶段的决定（和 6.4 是同一份文件）。Spec 轴的提示词要求对每条 `conflict` 和 `known-gap` 给结论：`accepted`（票允许这样做）、`must-fix`（同时进 `mustFix`），或 `needs-human`（不挡流程、不叫人，开 PR 时列在验收包和 PR 描述最前面，由合并人定）。结果加 `rulings`；有 `conflict` 或 `known-gap` 却缺结论，按 `invalid-output` 处理。需求级 final-review 同样处理整个需求的决定，判 `must-fix` 的走 final-fix。

**验收。** 用 3.4 的回放跑 T-25：Run 111 那条在票级被判 `must-fix` 或 `needs-human`。一条 `known-gap` 没有对应结论时，审查结果是 `invalid-output`。票的流水线和需求收尾两条路都覆盖。

### 6.3 审查之后的改动也要过一道检查（缺陷，P1）

**现状。** 票级审查只跑一次（[stage-flow.ts](../packages/shared/src/stage-flow.ts) 的 `reviewed`），review-fix、merge-fix 的改动不再审查，直接进集成分支；需求级的 final-fix 不复审；人正在验收时的 update-branch 也不经过审查。这几处都是 agent 在改别人的代码或测试：

- Run 129（S-11 的 update-branch，在 final-fix 之后）解决和 main 的冲突时，原话是「Main's list test that rejected status=pending,paid … was updated」和「The S-11 test that forbade documenting customer was inverted」：合并的同时改了 main 上已有测试的含义。
- Run 245（T-41 的 merge-fix）为了让门禁过，给同文件的 e2e 都加大了超时。覆盖层写着「不要靠改配置来让检查通过」，这次没人看。

**建议。**

1. worker 对每个会改代码的阶段的改动做一次确定性检查，不用 agent：(a) 删改了已有测试文件里的行（不是本票新增的测试）；(b) 改了测试或构建配置。(b) 的路径默认是一组常见配置文件，`gates.yaml` 可以补充。
2. 审查之后的阶段（review-fix、merge-fix、final-fix、update-branch）命中时，合并前跑一次 Recheck（只看这次改动的 Spec 轴）：对照票或需求和 6.4 的决策日志，只问一件事，有没有改变已有行为或放松检查。不命中就照现在直接合并。
3. Recheck 不是 pass：票 blocked、收尾 blocked、update-branch 走现有的 Spec 暂停，不再派 fix。人批准这次改动后接着跑；批准记成 Event，只对这一次改动有效。
4. 命中的改动和 Recheck 结论写进验收包最前面，例如「合并默认分支时改了这些已有测试」。

**验收。** merge-fix 改了一条已有测试的断言：合并前多一次 Recheck，不过就 blocked，批准后接着合并。只改源文件：不多跑。update-branch 和 final-fix 同样覆盖（需求收尾这条路）。

### 6.4 每张票一份决策日志，后面的阶段和下游票都读得到（效果，P1）

**现状。** 每个阶段都是全新会话，靠分支上的 commit 和 `/context` 接上前一步。[context.ts](../packages/pipeline/src/context.ts) 渲染的 `/context` 里没有之前各阶段的 summary 和决定，所以 gate-fix、merge-fix 不知道 implement 为什么那么做，可能悄悄推翻它（6.3 的 Run 129）。同一需求里的票之间也互相看不到：Run 435（T-61）写着「T-59 把 PR 字段叫 `pullNumber`，本票用 `pullRequestNumber`，两个都留着」，接口上于是多了一对同义字段。

**建议。** worker 给每个 agent 阶段渲染 `/context/decisions.json`：这张票之前各阶段的决定（带阶段和 Run 号），加上同一需求里已经 done 的票的决定（按票分组）。收尾的 final-review、final-fix 和 update-branch 拿到整个需求的。覆盖层补一句：要推翻其中一条时，记一条新的 `conflict`，写明推翻的是哪条、为什么。

**验收。** implement 写了一条决定，同一张票的 gate-fix 的 `/context` 里有它；上游票 done 之后，下游票的 `/context` 里有上游的决定；final-fix 拿到全部。

### 6.5 「留给别的票」在收尾前核对（缺陷，P1）

**现状。** agent 常写「这一部分留给后面的票」：Run 166、361、372、376，以及 Run 70 的「需另开契约票」。平台不核对后面的票有没有真的做，Run 70 说的那张契约票就从没出现。

**建议。** `deferred` 决定带 `ref`。收尾的 final-review Spec 轴拿到这个需求全部的 `deferred`，逐条判断有没有被某张票做掉。没做掉的不挡收尾、不叫人，开 PR 时列在验收包和 PR 描述最前面，由合并人选：追加一张票、接受不做、或记到下一个需求。

**验收。** 一条 `deferred` 指向 T-x，且 T-x 做了：收尾时不出现。`ref` 是 `new` 又没被做掉：收尾照常开 PR，验收包最前面写明。

### 6.6 门禁按测试名比，不按数量（缺陷，P1）

**现状。** 门禁要求测试总数不少于基准、跳过数不多于基准（[gate.ts](../packages/pipeline/src/gate.ts) 的 `countReasons`）。只比数字有两个问题：删一个测试再加一个，门禁看不出来；数字对不上时 agent 会去凑。Run 250（T-43 的 gate-fix）发现少的两个测试其实来自兄弟票，原话是「added tests rather than changing the baseline」。Run 229 也是兄弟票造成的差额。

**建议。** 基准改成测试名的集合（JUnit 的 classname + name，`gate_results.test_cases` 已经存了）：

- 票的门禁：分叉点上有、本票提交上没有的测试名，门禁失败，原因里列出名字。兄弟票后来加进集成分支的测试不算。
- 合并候选的门禁：按合并基点三方比，某一边有、另一边没有主动删掉的测试名少了，门禁失败；拿不到某一方的测试名时退回数量比较。
- 改名也算删除，覆盖层写明不要改已有测试的名字。
- 命中时 blocked（`tests-removed`）。人确实要删测试时批准这些名字，和批准保护路径是同一种动作：票上的批准进票的内容；收尾和 update-branch 上的批准只对那一次有效。
- 没有 JUnit、或 `gates.yaml` 声明按数量比的仓库（比如名字里带动态内容），退回现在的数量比较。

**验收。** 删一个测试、同时加一个：门禁失败，列出被删的名字。集成分支因为兄弟票多了测试、本票没有：不失败。合并候选少了某一边的一个测试：失败；main 那边已经删掉的测试：不算缺。

### 6.7 绕过和规划偏差按类型汇总，回流到规划（效果，P2）

**现状。** 同一类问题，每张票的 agent 都自己绕一次，没人修根因：

- 6 次 Run（286、363、372、376、402、423）写了迁移是手写的，多数的理由是「drizzle 的 snapshot 停在 0022」。
- Run 363、431、442：票的 `modules` 或正文写的文件不对，agent 改用了别的文件。
- 6.1 里「只改这个文件」和 tdd 的冲突出现了 5 次，说明拆票模板的写法会和 tdd 打架。

这些都是规划或仓库配置有问题的信号，现在散在各次 Run 的自由文本里。

**建议。** `workaround` 和 `conflict` 按项目汇总（先按关键词和相似文本归类），项目页列出「反复出现的绕过」，带次数和 Run 链接。人可以把一条变成规划输入：写进 `AGENTS.md`、建一个修仓库的需求，或改拆票模板。和 3.8「规范回流」合在一起做。

**验收。** 同一项目里出现 3 次以上相似的 `workaround`，项目页上有这一条，链到各次 Run。

### 7.1 Run 记下 token 用量（度量，P0）

**现状。** `runs` 表有 `token_usage`、`duration_api_ms`、`cursor_cli_version` 三列，[results.ts](../packages/api/src/stages/results.ts) 也接收这三个字段，但 worker 从来不发：[executor.ts](../packages/worker/src/executor.ts) 的 `agentFacts` 只交模型、skills 版本和提示词。Cursor 的用量就在事件流最后一条 `result` 事件里，[sandcastle.ts](../packages/pipeline/src/sandcastle.ts) 的 `onAgentStreamEvent` 每一行都看得到，只是没取出来。所以上面那张表只能从 Mac 上的日志文件里拼，日志一清理就没了，平台自己也算不出一个需求花了多少。

**建议。**

1. `SandcastleAgentRunner` 从 `result` 事件里取 `usage`（事件里有 CLI 版本和 API 耗时就一起取），放进 `AgentRunResult`，`agentFacts` 交给 API 写进 Run。
2. agent 跑完、后面失败的作业（例如推送失败）也要记：钱已经花了。
3. Run 页面显示这几个数；需求页汇总整份需求的用量，按阶段分开。
4. 历史 Run 不回填：日志目录名对不上 Run 编号，回填不划算。

**验收。** 假 runner 的事件流最后一行带 `usage`：Run 上有 `token_usage`；agent 跑完、推送失败的 Run 也有。需求页能看到按阶段的合计。

### 7.2 票级审查默认只跑 Spec 轴（token，P0）

**现状。** 每张票过门禁后跑两轴审查，各是一个完整的 agent 运行，各自读一遍 diff 和相关文件（[executor.ts](../packages/worker/src/executor.ts) 按 `REVIEW_AXES` 并行起两个）。需求收尾时，final-review 又按仓库把整份改动两轴再审一遍。4.15 说先做 4.2、4.3，再看数据决定；现在 4.2、4.3 都已上线，数据见上表：Standards 轴在两层一共 67 次，没有提出过一条必须修，票级 Spec 轴也是 0 条，有用的 4 条都在需求级 Spec 轴。票级审查约占 token 的 22%，每张票多等约 6 分钟。

**建议。**

1. 票级审查做成项目设置 `ticketReview`：`spec`（默认）、`both`，不提供 `off`（票级 Spec 轴要给 Ruling）。默认只跑 Spec 轴；Standards 轴只在 final-review 跑，那里看的是整份改动，坏味道也更容易看出来。
2. 只跑一轴时，`combineReviewRuns` 和 review-fix 读的 `review.json` 照常工作，没跑的那一轴不出现。
3. 改 [design.md](design.md) 里审查的段落，写清楚两层各审什么。验收包里的建议从此主要来自 final-review。
4. 票级 Spec 轴保留。它至今也是 0 条必须修，但原因是它看不到实现者的决定；第五轮的 6.2 让它对每条 `conflict`、`known-gap` 下结论，这才是票级审查该做的事。6.2 上线后，用 7.1 的用量算每条必须修和 `needs-human` 花了多少审查 token。

这一项取代 4.15。

**验收。** 默认设置下，一张票的审查只起一个 agent 运行（Spec 轴），final-review 仍是两轴；设成 `both` 时行为和现在一样。

### 7.3 按阶段选模型（token，P1）

**现状。** 模型按项目设一个（`projects.default_model`，没有就用 worker 的 `AFK_MODEL`，见 `runOptions`），所有阶段都用它。现在是推理档最高的 `cursor-grok-4.6-xhigh`：只读的审查、只合并默认分支的 update-branch、主要处理生成文件冲突的 merge-fix，都和 implement 用同一个模型。

**建议。** 项目设置加 `stageModels`，只认三个键：`standards`（两层的 Standards 轴）、`update-branch`、`merge-fix`，别的键报 400；没写的照旧用默认模型。键按角色不按阶段名：阶段名 `review` 同时包括两轴。Run 已经记了模型，加上 7.1 的用量，就能按模型比较每次的花费和结果。先换只读、机械的阶段：Standards 轴、update-branch、merge-fix。implement、gate-fix 和两层的 Spec 轴（6.2 之后要读决定、下结论）等 3.4 的回放有数据再动。这是 3.5「按策略升级模型」的静态第一步，和 2.9（提供方做成项目配置）用同一个设置入口。

**验收。** 给 `standards` 设了模型：Standards 轴的 Run 记的是这个模型，Spec 轴和其他阶段仍是默认模型；删掉设置后恢复默认；写别的键被拒绝。

### 7.4 长命令的输出不整段进上下文（token，P1）

**现状。** implement 的缓存读平均 511 万，是全部 token 里最大的一块。原因是会话长：平均 146 次工具调用，每一轮都把前面的上下文再读一遍。进了上下文的东西会跟着之后的每一轮走。全量测试一次返回约 9 万字符，本仓库 1900 多个测试的默认 reporter 输出，大部分是「通过」。gate-fix、merge-fix 也一样。

**建议。** 覆盖层「做事的边界」里加一条，和仓库语言无关：跑 `/context/run.json` 的 `gate` 命令或全量测试时，把输出写进文件，只看退出码、失败的部分和最后几十行，需要更多再按需读。单个测试文件的输出照常看。

收益要靠 7.1 来量：全量测试多在最后跑，后面剩的轮数不多，这一条的效果可能不大。量出来没有差别，就撤掉这条规则，不留着占提示词。

**验收。** 覆盖层的测试检查这条规则还在；7.1 上线后，比较规则上线前后同类票 implement 的平均缓存读。

### 7.5 GitHub 的 `commit_refs` 错误按网络错误重试（缺陷，P1）

**现状。** T-44 的 implement 跑了 22 分钟，最后推送时 GitHub 返回 `remote: fatal error in commit_refs`、`[remote rejected] … (failure)`。这是 GitHub 那边的偶发内部错误，不是分支被别人推过，也不是没有权限。[push.ts](../packages/worker/src/push.ts) 的 `NETWORK_PUSH` 只认连不上、超时和 5xx，这一条落进「被拒」，作业失败、重派，agent 从头再跑一轮。

**建议。** `NETWORK_PUSH` 加上 `fatal error in commit_refs`，以及 `remote rejected … (failure)` 这类没有给出原因的远端拒绝，按 4.6 的退避原地重试。明确的拒绝（`non-fast-forward`、`fetch first`、保护分支、没有权限）仍不重试，交给 5.1。

**验收。** 假远端第一次返回 `fatal error in commit_refs`、第二次成功：作业一次完成，agent 只跑一次；`non-fast-forward` 仍不重试。

### 7.6 gate-fix 直接拿到失败的用例（token，P2）

**现状。** gate-fix 读的 `/context/failure/gate.log` 是失败那一步输出的最后 200 行（[gate.ts](../packages/pipeline/src/gate.ts) 的 `FAILURE_LOG_LINES`）。门禁只在所有步骤都通过时才读 JUnit，测试命令失败时 `gate_results.test_cases` 是空的，agent 常常要再跑一遍全量才知道是哪几条。gate-fix 是单次最贵的修复：平均 19 分钟，输入 12.9 万。

**建议。** 失败的那一步是声明了 JUnit 的命令（没声明时是任一命令）时照样读 JUnit，把失败用例（文件、用例名、失败信息的头几行）写进 `/context/failure/cases.json`；gate-fix 和 merge-fix（合并后门禁失败）的提示词改成先只跑这些文件，修好后再按 `gate` 全量跑一次。5.4「重跑失败的测试」和 6.6「门禁按测试名比」用的都是 `gate_results.test_cases`，三项一起做。

**验收。** 门禁里两条用例失败：`cases.json` 列出这两条；没有 JUnit 的仓库不写这个文件，提示词照旧。

### 7.7 看过、决定不做的

- **精简提示词和覆盖层。** 平均约 3 千字符，不到一次审查输入的 1%。为省 token 去删它们，可能丢掉覆盖层回答 skill 提问的那些话，得不偿失。6.2、6.4 会往 `/context` 里加决策日志，也比 agent 自己读的文件小得多，用 7.1 的数据盯着就行。
- **去掉 agent 提交前自己跑的门禁。** 看起来和平台的门禁重复，但平台那一遍在干净沙箱里跑，是可信的检查；agent 那一遍挡掉的是 gate-fix，而 gate-fix 是单次最贵的修复。保留，只按 7.4 收窄它的输出。
- **implement 换模型或降推理档。** implement 约占 token 的 59%，但它直接决定质量。等 7.1 的用量和 3.4 的回放，再按 3.5 的策略决定。

### 7.8 丢租约计入失败次数（缺陷，P0，已做）

**现状（2026-11-12，S-33）。** 租约过期的作业被原样放回队列，`attempt` 加一，不算失败，可以无限重领。S-33 跑了 3 个半小时只完成 1 张票：宿主机直连 GitHub 时断时续，worker 里同步的 `git fetch` 一次卡 75 秒，几个槽轮流卡住，心跳连续失败，租约过期 21 次。作业 4782、4783 各被领了 7 次，agent 一遍遍从头跑，没有人知道。

**做法。** 领作业前，API 把租约过期的阶段作业记为失败（错误以 `lease-expired:` 开头），走和 worker 上报失败同一条路（`recordJobFailure`）：用新 key 重新排队，同一阶段累计三次失败就阻塞，叫人。不属于任何阶段的作业（host-sync、仓库权限检查等）照旧放回队列。事件的原因仍记 `lease-expired`，失败来源是平台。

**代价。** 重启 worker 时正在跑的作业也各记一次失败。

**还没做。** 根因是 worker 里访问远端的 git 是同步调用、没有超时，卡住时整个进程都停（`repos.ts`、`slots.ts`、`push.ts`）。这一条只是不让它无限重跑，根因要另外修。

## 评估方式

不预设未经测量的百分比目标。每项上线前后使用同一组样本和任务比较。平台方向里的成功标准衡量的是整个平台，靠 2.6 的度量来算；下表只用来比较单项优化的前后：

| 方向         | 观察指标                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------- |
| 人工处理     | 通知到首次操作、通知到恢复运行的时间；重复 blocked 次数；每个需求叫人的次数；自动重试后恢复的比例 |
| 接入         | 首次接入完成时间；卡在本机尚未检查、GitHub App 或门禁文件的次数                                   |
| 调度         | 几个需求同时运行时，每个需求从确认到第一张票开工的时间；有没有需求停在 running 却没有作业         |
| 页面性能     | 工作台与需求列表的查询耗时、响应体积、首次可操作时间                                              |
| 日志性能     | 不同日志大小的打开时间、追加耗时、内存峰值                                                        |
| 门禁         | 每张票的门禁次数和总时长；setup 占门禁时长的比例                                                  |
| 模型与提示词 | 回放评测里一次通过门禁的比例、fix 次数、耗时                                                      |
| 交付质量     | 合并前预警的命中与误报、验收时未验证标准被发现的比例；合并前要人补提交的比例、回滚率（需 2.6）    |
| 审查效果     | 票级与需求级必须修的条数之比；建议被处理的比例；每条必须修花的审查时长（4.2–4.4、4.15）            |
| 作业失败     | 每周因网络和鉴权失败而重跑的 agent 分钟数（4.6、4.7）                                             |
| 托管同步     | 每次 host-sync 的查询数和推出的 `invalidate` 数，对已合并需求数作图（4.13）                       |
| 票分支       | 推送被拒的次数和白跑的 agent 分钟数；人接手的次数；本地和远端分叉的次数（5.1、5.2）               |
| 不稳定测试   | 重跑后通过的门禁次数；花在不稳定测试上的 gate-fix 次数（5.3、5.4）                                |
| 合并冲突     | 合并冲突里只涉及生成文件的比例；merge-fix 次数和时长（5.5）                                       |
| agent 的决定 | 每张票的 `conflict`、`known-gap` 条数；开 PR 时仍是 `needs-human` 和没做掉的 `deferred` 条数；合并人对它们的处理（6.1、6.5） |
| 票级审查     | 票级与需求级必须修之比；`known-gap` 在票级被判 `must-fix` 或 `needs-human` 的比例（6.2）           |
| 审查后的改动 | 命中已有测试或配置改动的修复次数，其中 Recheck 不过、叫人的比例（6.3）                            |
| 测试名基准   | 门禁因测试名消失而失败的次数；其中人批准删除的比例（6.6）                                         |
| token 用量   | 每个需求、每张票按阶段的输入、输出、缓存读；每条必须修花的审查 token；换模型前后同类阶段的用量（7.1–7.4） |
| 白跑的 agent | 失败和超时作业的 agent 分钟数占比，按原因分（推送被拒、托管方错误、额度）（5.1、7.5）              |

本文不改变「人负责最终合并」「调度保持确定性」「agent 不直接改平台状态」等已定原则。
