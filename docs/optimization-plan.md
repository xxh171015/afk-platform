# AFK 平台优化建议与实施计划

2026-11-05 · 基于当前代码与设计文档的静态评估

## 定位与结论

AFK 平台已经具备「规划与拆票 → 按依赖调度 → 沙箱执行 → 门禁与收尾 → 人工验收」的主链路。现有实现中，作业租约与 fencing、真实 Postgres 测试、按包划分的依赖方向、结构化简报和工作台，都是值得保留的基础。

下一轮优化应服务于两个结果：**人被叫回来时能迅速做对决定**，以及**需求、Run 和日志积累后仍能稳定使用**。本文是优化建议，不替代 [总体设计](design.md) 或 [操作体验 spec](specs/experience-platform.md)；涉及 M3–M5 的建议以现有里程碑为前提。

本次只读了代码和文档，没有开展真实用户走查、运行压测或生产故障分析。因此性能问题是有代码依据的风险，具体阈值须先测量，不能当作已发生的故障。

## 优先级总览

| 顺序 | 事项 | 类型 | 预期收益 | 启动条件 |
| --- | --- | --- | --- | --- |
| P0 | 待处理决策卡与排序 | 用户体验 | 减少定位问题和选择动作的时间 | 现在 |
| P0 | Run 日志增量解析与可见区域渲染 | 架构与体验 | 长 Run 页面保持可用 | 先建立日志样本和浏览器基线 |
| P1 | 首次接入状态检查 | 用户体验 | 降低接入时的排障成本 | 现在 |
| P1 | 列表和工作台有界查询 | 架构 | 控制数据增长后的查询与传输成本 | 先建立数据规模与耗时基线 |
| P2 | 窄屏任务视图 | 用户体验 | 在小屏幕上完成查看与处理 | 确认小屏使用频率后 |
| P2 | worker 阶段模块接口收拢 | 架构 | 降低新增阶段、执行器时的修改范围 | 下一次改动执行流水线时 |
| M3 前 | 远程部署身份与事件方案 | 架构 | 支持远程 worker 和多实例 API | 决定迁服务器时 |
| 探索 | 风险预演、验收差距视图、处理建议学习 | 创新 | 提前暴露风险，形成可验证的反馈闭环 | 核心体验稳定后 |

P0/P1 是建议优先级，不表示已排期。每项先有可观察的基线，再设目标值。

## 1. 用户体验优化

### 1.1 待处理：从分类列表变成决策入口（P0）

**现状。** [待处理页面](../packages/web/src/BlockedQueue.tsx)已有类别筛选、结构化简报、重试说明和危险操作确认；[工作台](../packages/web/src/Workbench.tsx)也能显示等待数量。但待处理列表按类别铺开，缺少跨类别的统一优先级。人仍要逐张卡判断影响范围和处理顺序。

**建议。** 给每个待处理项形成统一的展示模型：`发生了什么 / 阻断了什么 / 建议动作 / 证据 / 可执行动作`。排序先用确定性规则，例如「阻断其他票或收尾的事项优先、已经等待较久的事项优先」；不要让模型直接决定调度优先级。支持按需求或仓库收拢，保留原有类别筛选。

**实施步骤。**

1. 在页面数据层产出统一的待处理项模型，保留原始原因码和 Run 指针。
2. 用现有票依赖与 Spec 状态计算影响范围，避免另建一套手工维护的优先级字段。
3. 先上线只读的排序与说明，再根据实际操作记录调整规则。

**验收。** 用户从工作台进入待处理后，无需打开多张详情页，就能知道首项为何排第一、该做什么、证据在哪；操作后卡片消失或明确说明仍被什么阻断。记录「通知到首次操作」和「通知到恢复运行」的时间分布，作为改进依据。

### 1.2 首次接入：显示检查结果，而不只给命令（P1）

**现状。** [接入页面](../packages/web/src/Onboarding.tsx)提供锁定版本的安装命令和 `/afk-setup` 指引；项目数查询失败时，它仍显示折叠的「接入新项目」入口，故障与已有项目两种情况没有明确区分。

**建议。** 把接入过程展示成「平台可达 → 安装 skills → 注册仓库 → GitHub App 权限 → 门禁检查」的状态清单。已知状态由现有接口读取；无法验证的步骤明确标为「尚未检查」，并给出可复制的检查命令。项目数读取失败应直接显示错误与重试。

**验收。** 新用户能从页面判断卡在哪一步；API 故障不会被误认为接入完成；所有指引都能定位到一个可执行动作。

### 1.3 窄屏：提供任务视图（P2）

**现状。** [需求列表](../packages/web/src/SpecList.tsx)在窄屏下保留最小宽度 1200px 的表格并横向滚动；样式文件仅对侧栏、顶栏等做了收缩。当前桌面优先的定位是合理的，但小屏阅读和处理会比较费力。

**建议。** 在窄屏下用卡片显示编号、标题、状态、进度和下一步；完整列留在桌面表格。优先保证「查看待处理、打开证据、执行简单恢复动作」，不必把依赖图编辑等桌面任务搬上手机。

**验收。** 320–640px 宽度下，查看待处理和进入票详情无需水平滚动；主要按钮可触达，长标题和错误信息不会遮挡操作。

## 2. 架构优化

### 2.1 列表与工作台查询按用途收敛（P1）

**现状。** [需求列表查询](../packages/api/src/tickets/views.ts)聚合所有 Spec 和票，没有分页；前端再完成筛选、排序。[工作台查询](../packages/api/src/tickets/workbench.ts)复用全量 Spec 列表，另取待处理、运行票、验收包，并对历史 Run 按项目和阶段计算均值。小规模时逻辑清楚，规模增长后每次刷新都要重复处理历史数据。

**建议。** 先用代表性数据测量 `/specs` 和 `/workbench` 的数据库耗时、响应体积及页面渲染时间。随后分别为「分页浏览需求」和「工作台当前事项」设计较小的接口：列表用游标或稳定排序分页；工作台直接查询活跃、待验收和最近完成的有限集合。历史阶段均值可按完成事件增量维护，或在有证据表明查询昂贵时再缓存。

**验收。** 数据量增加一个数量级时，首页返回的数据量仍有上限；列表翻页无重复、无遗漏；SSE 失效和断线轮询仍能得到正确结果。数据库查询计划与页面耗时在变更前后留档。

### 2.2 Run 日志只解析新增内容（P0）

**现状。** [RunLog](../packages/web/src/RunLog.tsx)按 offset 拉取日志，但把新文本追加到 `position.text` 后，每次渲染都对全文执行 `groupLog`。服务端允许每个 Run attempt 最多 [50 MiB](../packages/api/src/logs/log-store.ts) 日志；长 Run 会同时增加字符串复制、解析和 DOM 渲染成本。

**建议。** 把日志解析做成以「当前 offset、未完成行、已完成 block」为状态的增量模块，接口只接收新 chunk 并返回新增 block。页面只渲染可见窗口，保留「跟随最新」「展开原始事件」「切换 attempt」现有语义。解析模块的接口应能用完整日志与分段日志得到同一结果。

**验收。** 用脱敏的真实日志样本覆盖短日志、长日志、半行切片、中文跨字节边界和 attempt 变化；分段解析结果与当前 `groupLog` 一致。记录 1/10/50 MiB 样本下的首次打开时间、追加 chunk 耗时和浏览器内存峰值，再决定是否需要 Web Worker。

### 2.3 收拢 worker 阶段模块接口（P2）

**现状。** [executor.ts](../packages/worker/src/executor.ts)同时负责 agent 修改、review、gate、merge、e2e、diagnose 及环境准备，文件已超过千行。现有测试覆盖较多，但新增执行器或阶段时容易跨多个流程修改。

**建议。** 在下一次扩展流水线时，先定义一个面向 worker 循环的阶段执行接口，例如「输入任务上下文与取消信号，返回阶段事实」。按阶段拆开实现，环境、日志、凭据和租约检查留在共同的内部模块。先迁一个阶段验证接口，再迁其余阶段；避免只为缩短文件而增加转发层。

**验收。** worker 循环调用方式保持稳定；新增阶段时不用修改已有阶段的内部逻辑；原有租约丢失、重试、门禁与合并测试继续通过。

### 2.4 迁服务器前明确身份与事件机制

**现状。** API 只监听本机且无登录，这是当前单人 PoC 的明确选择；[SSE 事件](../packages/api/src/events/hub.ts)只在单进程内传递。[总体设计](design.md)同时提到 M3 迁服务器、M5 登录权限，具体部署时点需要定稿。

**建议。** 在 M3 的部署方案中一次性决定：页面用户、CLI、worker 分别如何认证；worker 的租约凭证与仓库访问权限如何隔离；多 API 实例时事件如何跨实例投递；哪些状态变化必须保证最终可见。若 M3 仍保持单 API 实例，也应把这一限制写进部署约束，不提前引入事件总线。

**验收。** 远程 worker 无法冒用其他 worker 的租约；未授权客户端不能读取 Run 日志或执行恢复动作；API 重启与 SSE 断线后，页面能通过现有轮询回退恢复正确状态。

## 3. 创新点子与验证方式

### 3.1 合并前风险预演

利用票依赖、模块重叠、分支头和门禁结果，给出「潜在冲突」「契约版本落后」「该仓库 PR 还在等待上游合并」等提示。每条提示必须附上可检查的事实和对应票、Run、分支链接；只做预警，不自动改写依赖图。总体设计已经把 trial-merge 与跨需求冲突列入 M3，此处建议先验证提示能否减少人工返工。

**小试验。** 在两个并行需求上记录平台提前提示的风险、实际发生的冲突与误报；误报过多则缩小规则，不扩大自动化权限。

### 3.2 验收差距视图

在现有验收包之上增加一个汇总：每项验收标准的状态、证据 Run、未验证原因、人工放行记录。优先显示未验证和被放行项，并保留按仓库查看。它是现有验收包的读法改进，不另造一份验收数据。

**小试验。** 让用户用该视图完成一次跨仓库验收，记录从打开交付页到完成决定的时间，以及是否仍需反复查日志或 PR。

### 3.3 处理建议的反馈闭环

对 blocked 原因码记录「推荐动作 → 人实际选择的动作 → 是否恢复 → 是否很快再次 blocked」。先做规则统计和人工可见的历史案例，不让模型直接决定重试或放行。M4 的追溯链路可为这项能力提供上下文。

**小试验。** 聚焦出现频率最高的两个 blocked 原因；只有当历史样本足够、建议明显优于当前固定文案时，再考虑更复杂的推荐方式。

## 建议的推进顺序

1. **一周内可启动：**选 3–5 个真实的 blocked 案例，画出待处理决策卡；修正接入页的错误状态；收集 1/10/50 MiB 日志样本和页面耗时基线。
2. **下一轮实现：**上线待处理排序与解释；完成日志增量解析和可见区域渲染；为列表与工作台建立数据库及页面性能基线。
3. **规模或部署触发：**数据增长后做分页和有界工作台查询；M3 迁服务器前定稿身份与事件方案；扩展流水线时收拢 worker 阶段模块接口。
4. **试点验证：**在真实跨仓库需求中试风险预演和验收差距视图，只保留能减少返工或缩短验收时间的能力。

## 评估方式

不预设未经测量的百分比目标。每项上线前后使用同一组样本和任务比较：

| 方向 | 观察指标 |
| --- | --- |
| 人工处理 | 通知到首次操作、通知到恢复运行的时间；重复 blocked 次数 |
| 接入 | 首次接入完成时间；卡在权限或门禁步骤的次数 |
| 页面性能 | 工作台与需求列表的查询耗时、响应体积、首次可操作时间 |
| 日志性能 | 不同日志大小的打开时间、追加耗时、内存峰值 |
| 交付质量 | 合并前预警的命中与误报、验收时未验证标准被发现的比例 |

本文不改变「人负责最终合并」「调度保持确定性」「agent 不直接改平台状态」等已定原则。
