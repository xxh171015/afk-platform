# 规划文档随需求进 PR，由平台提交

grill 改的术语表、ADR 和 `AGENTS.md`（规划文档）不由人提交、也不由人推送：`plat spec confirm` 在规划仓库里把它们相对远端默认分支的改动作为补丁发给平台，平台在任何票开工前把补丁三方合并到规划仓库默认分支的最新提交上，作为这个 Spec 集成分支的第一个提交（规划提交），文档跟着代码在同一个 PR 里进默认分支。替代 [ADR 0003](0003-pointers-not-copies-include-sandbox-mounts.md) 里「规划提交由人在规划仓库里做、推到远端、confirm 核 SHA」的部分；0003 的「存指针、不复制，沙箱挂载不是第二份正文」不变。

## Considered Options

- **人提交并推到默认分支**：需求还没开发，文档先进了默认分支；试点仓库的直推检测也会标红。
- **人提交并推到一个远端分支，confirm 核 SHA（#139 的做法）**：不进默认分支了，但人还得在需求开发前单独提交、推送一次只有文档的改动。
- **confirm 替人提交并推到 `planning/<spec>` 分支**：人不用动手，但开发还没开始，代码仓库里就先出现一个只有文档的分支。
- **让规划 agent 按 tracker 文档去 git commit / push**：每个人的 agent 做法不一，不可控。
- **把文档正文存进平台、一直从平台挂载**：违背「存指针」。

## Consequences

- 平台短暂持有补丁：确认时收下，规划提交做成（或放弃、或 Spec 取消）就删掉，之后只存规划提交的 SHA。
- 规划仓库在 `plat spec create` 时记到 Spec 上（CLI 从 tracker 文档第一行读出），页面确认也知道规划仓库，只是带不上本地改动。
- 补丁合不进默认分支时 Spec 停在开工前，等人 `plat spec retry-planning`（本地解决后重新发送）或 `plat spec waive-planning`（不要了，验收包和 PR 描述注明）。
- 规划仓库没有本需求的票、但提交了规划文档时，收尾照样给它开一个只有文档的 PR。
- 没有规划文档改动时，规划提交就是规划仓库默认分支当时的最新提交，其他仓库的票照样在 `/context/domain/` 读到术语表和 ADR。
