# 事件由数据库触发器写，来源由 API 在事务里告诉触发器

事件要和状态变化**同一事务**写入，覆盖需求、票、作业、收尾、最终 e2e、规划提交和 PR 的每次状态变化。API 里改这些状态的 SQL 有六十多处，分散在调度、worker 回报、host-sync、人的操作里。所以事件不由这些代码各自去写，而由数据库触发器写（`packages/api/drizzle/0035_events.sql`）：状态列一变，触发器在同一条语句里插一行事件，从什么到什么取自 `OLD` / `NEW`。事务回滚，事件跟着没有；以后新加一处改状态的代码，也不会漏记。

谁做的改动，触发器自己看不出来。API 用 `AsyncLocalStorage` 记下当前请求或调度轮次的来源（`packages/api/src/events/origin.ts`）：`/worker/*` 是 worker，带 `x-afk-client: cli` 的是 CLI，其余是页面；worker 回报的是 host-sync 作业时改成 host-sync；调度轮次不管跑在谁的事务里都记成调度器。`inTransaction` 开事务后用 `set_config(..., true)` 把来源和作业号设成事务内的变量，触发器读它们，作业号再换成 Run。

失败来源按原因码算好存下。对应表放在 `@afk/shared`（`failure-source.ts`），页面和待处理队列用它；触发器用迁移里的 `afk_failure_source()`，是同一张表的 SQL 版本，测试逐个原因码和一组真实错误样本核对两边一致。改对应表要连同一个替换这个函数的迁移。

人的操作（重试、放行、取消……）不是状态列的变化，由操作的代码在同一事务里显式插入事件。

## Considered Options

- **在每处改状态的代码旁边调用 `recordEvent()`**：六十多处都要先查出旧状态再写，很多处现在不在事务里，要一并改；以后新代码漏调就漏记，测试也难发现。
- **触发器里不算失败来源，由 TypeScript 在提交前补上**：对应表只有一份，但要在事务提交前再扫一遍本事务的事件去改，"只追加"变成了"提交前可改"，事务外的写入还会漏补。
- **每个来源用一个连接池，在连接上设来源**：页面和 CLI 走同一批路由，按池区分不了；连接数也翻几倍。

## Consequences

- 不在事务里（自动提交）的状态写入，事件照记，但来源为空。改状态的地方应放进 `inTransaction`；认领作业时标记票开始已经改成这样。
- host-sync 作业本身不触发事件（例行轮询不记），它发现的 PR 变化照记；只改 `synced_at` 不算变化。
- 事件表没有外键，不随需求或作业删除；永久保留。
