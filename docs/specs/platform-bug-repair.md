# 平台自身 bug 自动接单与修复

**技术方案 · 待评审 · 2026-11-16**

建议先在 AFK 自己的 GitHub 仓库试点。维护者在一份普通功能 bug 报告上加接单标签，代表同意平台为这次报告花预算、复现问题，并在证据成立时自动确认一张实现票。平台交付修复 PR，维护者决定是否合并。上线后由维护者验证原症状并关闭 Issue。

**评审时最值得定的三件事**是接单标签授予多大权限、什么样的复现足以开工、平台交付到哪一步。下面给出可直接试点的默认值。

## 1. 从一份报告看使用体验

假设有人报告「控制塔切换项目后，待处理列表仍显示上一个项目的票」。报告写明操作、实际结果、预期结果，最好附平台版本或 Run 编号。维护者判断预期明确，给 Issue 加上 `bug`、`ready-for-agent`。

1. 平台接单，在 Issue 留下一条状态评论，写明对应的 S 编号。后续更新这条评论。
2. 平台读取代码和报告，在沙箱写一个用户行为测试。用同样的操作切换项目，旧代码确实保留了错误的票。平台记录测试、失败断言和运行时的提交。
3. 平台在该 bug Spec 下生成一张 `implementation` Ticket，验收条件是项目切换后只出现目标项目的票，同一个测试通过。现有流水线实现、审查并收尾。
4. 维护者从 Issue 点进 PR，可见旧提交上的失败、新提交上的通过、原因解释及代码改动。如果报告只说「列表不对」，平台返回缺少的复现条件。外部服务中断或需要做产品取舍时，也给人明确的调查结果。

这个例子用于说明验收行为。试点覆盖 AFK 单仓库内能用 Vitest 验证的功能回归，包括 HTTP、CLI、控制塔交互和导出函数。生产事故、安全问题、数据迁移、多仓库改动以及需要真实生产数据的问题交给维护者。现有保护路径的修改仍须人决定。

## 2. 怎样接到现有平台

| 环节 | 已有能力 | 首期改动 |
| --- | --- | --- |
| 报告进入平台 | `plat bug` 和 `POST /bugs` 建立 bug 草稿并排 Locate。[实现](../../packages/api/src/planning/locate-bug.ts) | 引入 GitHub Issue 与 Spec 的唯一绑定，抽取可在同一事务内调用的创建逻辑。手工入口沿用原行为。 |
| 找到相关代码 | Locate 只读。worker 在选定文件上做 blame 并解析 trailer。目前缺少原 Spec 会记作 `bug-unlocated`。[worker](../../packages/worker/src/stages/locate.ts) · [结果处理](../../packages/api/src/planning/locate-bug.ts) | 单独保存「报告与文件的对应证据」和「追到的原 Spec」。在接单来源下，文件与症状有依据即可尝试复现，允许 `source_spec_id` 为空。 |
| 拆票与确认 | 导入负责校验票正文、存内容版本。确认负责仓库权限、规划提交、集成分支和调度。[导入](../../packages/api/src/planning/planning.ts) · [确认](../../packages/api/src/scheduling/scheduler.ts) | 对一份已授权、已复现的单仓库报告，生成固定格式的一张实现票，调用同一套导入和确认逻辑。保留 `fix` 类型用于联调失败后的 Fix ticket。 |
| 提交与验收 | 票有门禁、审查、集成分支合并，Spec 有收尾、验收包和 PR。现有自动合并策略只适用于 improvement。[票阶段](../../packages/shared/src/stage-flow.ts) · [收尾](../../packages/shared/src/finalize-flow.ts) · [合并策略](../../packages/shared/src/auto-merge.ts) | 对带接单记录的 Spec 增加复现证据校验，验收包附上证据和来源链接。bug PR 由人合并。 |

## 3. 入口、授权与状态回写

试点配置绑定一个已登记的项目、一个 GitHub 仓库及其稳定仓库 ID、一组可授权的维护者 GitHub 用户 ID。初始关闭。现有 `host-sync` 随运行中的 Spec 或 PR 工作，空项目也要能接第一单，因此 API 周期调度独立的 `bug-issue-sync` 托管作业。每仓库复用一行作业，建议每五分钟执行一次。由带相应能力的 worker 持安装令牌访问 GitHub，API 和 agent 沙箱不持这个令牌。[现有托管作业](../../packages/api/src/host/host-jobs.ts) · [worker 执行入口](../../packages/worker/src/host.ts)

worker 分页读取同时带两个标签的开放 Issue，排除 PR，检查最近一次有效的 `ready-for-agent` 加标事件。授权来自维护者名单中的真人。只接受启用试点以后加的标签，避免导入历史积压。完成这一轮分页再更新扫描进度，限流按 GitHub 的重试时间退避。已接单且尚未确认的 Issue 单独按编号回读，能发现关单和撤标。选择轮询是为了适配当前本机部署，未来有公网入口时可以把 webhook 接到相同的接单操作。[GitHub Issues](https://docs.github.com/en/rest/issues/issues#list-repository-issues) · [标签事件](https://docs.github.com/en/rest/using-the-rest-api/issue-event-types#labeled) · [请求与限流建议](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)

接单时冻结标题、报告正文的限长脱敏快照、授权事件 ID 和快照摘要。报告只作为问题材料，不从正文取可执行命令、仓库地址、凭据或已批准的路径。自动确认前，worker 再读取 Issue 并提交一次带版本的授权检查。若已关闭、撤标或报告正文改变，停止确认，记录原因，要求维护者按新正文重新加标。已经确认的票按冻结版本运行，维护者可用现有 `plat spec cancel` 立即停止。GitHub 和 Postgres 不能跨系统加锁，界面要明确显示最后一次授权检查的时间。

Issue 评论使用固定模板，只写阶段、阻塞原因、S/T 编号和 PR 链接。详细日志留在平台。PR 以普通链接引用 Issue，避免合并触发自动关单。评论回写作为独立托管作业，失败可重试。worker 只编辑本应用创建且含本实例标记的评论，创建后丢失响应时先查回已有评论。安装授权按功能增加 Issues 权限，扫描申请只读令牌，回写申请可写令牌。仅对启用接单的仓库检查这两项能力。[当前令牌权限](../../packages/host/src/types.ts) · [GitHub 评论接口](https://docs.github.com/en/rest/issues/comments#create-an-issue-comment)

## 4. 怎样证明问题复现、修复有效

**把复现放在自动确认之前。** 新增一个 Spec 级 `reproduce-bug` 作业。它有自己的 Run 和预算，在默认分支固定 SHA 的一次性槽位中工作。Locate 的文本是线索，复现产物是一份可以由另一台 worker 重跑的测试。首期只接收一个新增的普通 `*.test.ts(x)` 文件和一个明确命名的用例，保护路径、符号链接、已有文件覆盖和超限文件均拒绝。需要复杂夹具的报告返回人工处理。

| 步骤 | worker 负责的验证与持久化 |
| --- | --- |
| 生成测试 | agent 根据报告和 Locate 结果，用项目公共接口表达预期，仅输出测试文件、用例名、对应预期和根因假设。worker 从槽位取出文件并检查实际 diff。保留通过校验的文件内容、相对路径、内容摘要和基准 SHA，随报告存储。 |
| 证明旧代码失败 | 在两个独立干净沙箱，各取相同基准和同一测试文件。使用可信基准上的 setup 与固定的按文件测试命令，测试路径作为独立参数。要求两次都有指定用例的 JUnit 记录、同一行为断言失败，记录期望值、实际值和错误类别。编译错误、导入失败、用例缺失、超时、网络故障和偶发失败均不能作为红证据。无法可靠区分断言与环境错误时转人工。 |
| 开工 | API 校验目标仓库、接单授权、复现结果和预算，生成票正文。正文含症状、预期、根因假设、证据 Run、验收条件，自动批准的保护路径和删除测试列表均为空。确认指向已登记的规划仓库，规划补丁为空。每个实现 Run 重新取得冻结的测试，放进票分支并纳入交付。 |
| 证明新代码通过 | worker 校验测试路径和内容摘要，在候选提交上执行同一用例，要求 JUnit 明确记录通过。随后走全量门禁与既有审查。审查者核对测试断言能否表达报告的预期，代码差异能否解释红到绿。两次断言失败本身只能证明症状可重现。 |
| 保持证据有效 | 单票 gate、合入集成分支的候选、收尾改动和 Update-branch 都使用同一个证据检查。按最终 PR head 查找通过记录，SHA、测试摘要、执行环境或可信配置改变即重新验证。被丢弃的 Tidy 候选沿用原集成分支的有效记录。开 PR 时再次核对远端 head，发生变化先重验，已开 PR 的验收包标明最后验证的 SHA。 |

复现 SHA 与实现起点可能不同，例如排队时 main 前进或 Planning commit 包含设置提交。开始改产品代码前，在实际起点重跑冻结测试。若已经通过，记录「当前起点已无法复现」并交人核实，避免为过时报告造改动。若两次都仍按同一断言失败，记录新的基准并继续。所有验证沿用隔离沙箱和临时 Postgres，测试过程使用测试数据。目标测试必须实际执行，普通门禁的缓存命中或仅汇总测试数量不足以生成这份证明。[门禁与 JUnit](../../packages/pipeline/src/gate.ts) · [仓库门禁配置](../../.sandcastle/gates.yaml)

## 5. 状态、数据和恢复

接单只管理确认前的过程。建议在 Postgres 增加 `bug_intakes`，以 `(repo_id, github_issue_id)` 唯一，同一 Spec 最多一条，原 Spec 关联仍由 `specs.source_spec_id` 保存。不同 Issue 描述相似时交维护者判断重复。首期按来源 ID 去重。数据库约束确保目标 Repo、Spec 属于同一 Project，自动接单只能绑定 bug 类型 Spec。

| 接单状态 | 进入条件 | 离开方式 |
| --- | --- | --- |
| `locating` | 来源通过校验，已绑定草稿并排 Locate | 有单仓库代码线索进 `reproducing`，信息不足进 `needs-human` |
| `reproducing` | 开始生成用例或重放基准 | 红证据成立进 `ready`。无法稳定复现、非代码问题或预算耗尽进 `needs-human` |
| `ready` | 存好冻结测试，等待授权复核与确认 | 复核通过后导入一张票并确认，进入 `handed-off`。授权撤回进 `withdrawn` |
| `needs-human` / `withdrawn` | 证据不足、超范围、维护者撤回或报告已改 | 原因回写 Issue。在仍为草稿时，经新的有效加标事件可在同一 Spec 重试，递增 attempt，旧 Run 留档。已取消则保留终态，由人决定后续需求。 |
| `handed-off` | Spec 已确认 | 进度直接读取 Spec、Ticket、PR。合并后回写「已合并，待上线验证」。 |

从任意确认前状态都能撤回。持久化接单来源、授权人和事件、快照摘要、当前 attempt、原因、证据 Run ID、评论 ID 和修订号。每轮复现的测试原文与证据按 attempt 保存，建议单文件上限 64 KiB。旧 attempt 的迟到回报不得恢复授权或替换当前证据。控制塔和 `plat spec show` 展示来源、预期、红绿证据和失败原因，所有需要人处理的接单在待处理队列只列一次。

**事务切点。** 当前 `submitBug` 创建草稿和排 Locate 分两次提交，导入与确认也各自管理事务。实现时抽取接受同一数据库 client 的内部操作，保留原入口的事务包装。第一次事务原子完成「来源占位、建草稿、排 Locate」。确认事务锁住来源与 Spec，校验当前 attempt、输入摘要、授权复核结果、已存证据和开关，再完成「导入、确认、标记 handed-off」。遇到校验失败回滚整组写入。稳定幂等键包含来源、attempt 和操作名，外部网络读写均在事务外。确认和状态事件记录平台调度来源、授权人及证据，避免把自动确认显示成人在 CLI 操作。[队列](../../packages/api/src/jobs/queue.ts) · [事件来源](../../packages/api/src/events/origin.ts)

**恢复与停止。** worker 回报沿用租约和 attempt 校验，重启后新 worker 从冻结的输入和测试继续。周期调度扫描未完成的绑定以恢复未发出的托管作业。已有 24 小时 bug 草稿清理应排除有接单绑定的草稿，避免周末待补信息时被自动取消。建议试点默认每次仅调查一单，每日最多新接三单，每轮一份测试，复现 agent 最长 15 分钟。超额报告留在来源等待下轮，确认后的执行沿用项目并发和预算。来源作业遇临时网络错误最多重试三次，之后保留失败与最近成功同步时间，供人恢复。停用开关立即阻止新接单及未确认草稿转执行，已确认的 Spec 可独立取消。平台整体不可用时，原 Issue 仍在，维护者可照常手工修复。

## 6. 实施与验收

| 顺序 | 实现范围 | 可独立验收的结果 |
| --- | --- | --- |
| 1 · 只接单和定位 | `host` 增 GitHub Issue 读写，`worker` 执行托管作业，`api` 持久化来源、查重、排 Locate，`shared` 定义校验结构。配置默认关闭，先启用仅调查模式。 | 一份授权报告在 Issue、控制塔和 Spec 间可互相找到。重复扫描和 API 重启仍只有一个草稿。 |
| 2 · 复现与人工抽查 | `pipeline` 实现隔离运行和 JUnit 证据判定，`worker` 固定输入并回传，`api` 保存每次结果。仅调查模式到 ready 为止。 | 选一个有已知答案的平台历史问题，由维护者检查红测试是否测到了报告中的行为。再用一个环境故障检验平台会交人处理。 |
| 3 · 自动执行到 PR | 接入事务内导入与确认、票级和需求级验证、验收包及评论回写。开关切到「自动到 PR」仅对该模式下新授权的报告生效。 | 一份真实单仓库报告交付可评审 PR，可按 SHA 重放同一红绿测试。回写失败可单独重试。 |

实现时，API 路由与 worker bundle 修改需生成 OpenAPI 和客户端类型，Drizzle 表和约束变更需生成 SQL。新行为先以公共接口写测试。API 使用真 Postgres，GitHub HTTP 和 agent 运行器可使用边界假对象。以下场景作为上线门槛。

- **一次接单。** 同一 Issue 被两个 worker 重叠扫描、掉线重送，最终只有一个 Spec、一张 Ticket 和一次自动确认。无授权、bot 加标、其他仓库、PR 或历史标签均不会触发。手工报告仍只建草稿并执行既有 Locate。
- **有据才改。** 旧代码缺少 Spec trailer 但用例稳定复现时能开工。基准已绿、用例跳过、编译失败、外部凭据失效、产物越界或不稳定时返回具体原因，自动确认次数为零。
- **证据跟随最终代码。** 单票修复、合并候选及 final-fix、Tidy、Update-branch 后，替换或移除冻结测试、目标用例未通过、验证记录属于旧 SHA，均不能作为当前 PR 的通过证明。已有门禁、审查、保护路径和测试删除检查仍须通过。
- **能停能续。** 验证中撤标、改报告、关 Issue、关闭功能或 Spec 被取消时，迟到回报不能继续开工。草稿跨过 24 小时仍能处理。基础设施恢复后能在原单上重试，评论失败不会重新修一次。
- **交付可核对。** 即使项目启用 `auto-improvement`，此 PR 仍等人合并。验收包列出来源、预期、根因假设及证据、红绿 Run 和 SHA、保护路径检查结果、剩余疑点。试点统计接单数、稳定复现比例、报告到 PR 的时间、agent 分钟和人工拒绝原因，以实际样本决定下一阶段范围。

## 7. 本轮评审决策

| 决策 | 推荐值 | 代价 |
| --- | --- | --- |
| 谁能授权开始修 | 指定维护者给单仓库 Issue 加 `bug` 与 `ready-for-agent`，一次授权覆盖调查及符合条件的单票确认 | 维护者要先分诊，但不用再为同一份合格报告手工拆票 |
| 首期接哪些问题 | AFK 自身、单仓库、一个新增行为测试可以稳定复现的普通功能 bug | 历史数据、跨服务、偶发问题的覆盖率较低，保留调查结果供人继续 |
| 怎样交付 | 到带红绿证据的 PR 为止，人工合并、部署及验证后关 Issue | 需人工确认线上结果。下一期接入部署 SHA 和症状观测后，再设计自动结单 |
