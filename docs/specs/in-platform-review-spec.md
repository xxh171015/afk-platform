来源：grilling 共同理解（人审意见以平台为准，[ADR 0012](https://github.com/xxh171015/afk-platform/blob/main/docs/adr/0012-review-comments-are-platform-authoritative.md)）。技术方案细节在规划文档《在控制塔里审代码》。

## Problem Statement

人要验收一个需求，现在得从控制塔跳到 GitHub / GitLab 看 diff、写评论。平台读不到这些评论的正文，改动只能靠在规划机器上追加票。交付页还写着「平台从不合入」，和已经开了自动合并的项目不符。自动合并只靠上一轮 host-sync 的快照，PR 在这一分钟里被转成草稿、被人评论或换了 head，仍可能去改描述并尝试合并。

人想在控制塔里找到等着审的需求，按导读看完全部代码改动，在代码上写下意见，一次交给平台；agent 改完、过门禁、更新 PR 之后，需求再回到等人验收。合并仍在代码托管上做。

## Solution

控制塔增加待审列表和审查页。平台用 git 为每个 PR head 算出一份审查版本（diff、逐行归属、文件内容），按需求 → User Story → 票的依赖序拼出导读，不为导读跑 agent。人在 diff 上写人审意见（先是草稿），一次提交成修改要求：需求进入 finalizing，有意见的仓库各跑一步 Rework，只过门禁和（命中时）Recheck，不重跑 final-review。托管上只留一条平台维护的汇总评论。Rework 结束后需求回到 awaiting-review。有过已提交人审意见的需求不再自动合并。

## User Stories

1. 作为验收的人，我想在侧栏看到「待审」，和「待处理」分开，这样我不会把等人审的需求和卡住的票混在一起。
2. 作为验收的人，我想「待审」排在「待处理」前面，这样我先处理验收，再处理 blocked。
3. 作为验收的人，我想用 `g r` 打开待审、`g b` 仍打开待处理，这样快捷键和现在的习惯一致。
4. 作为验收的人，我想待审角标只数「等你审」和「审到一半」，这样返工中的需求不会一直红点。
5. 作为打开工作台的人，我想「等你验收」不再列出每条需求，而是一行「n 个要看」链到待审，这样工作台只做入口。
6. 作为打开工作台的人，如果还有看完待合并的需求，我想看到「另有 n 个待合并」，这样我知道还有 PR 要到托管上合。
7. 作为跨项目工作的人，我想待审列出所有项目里等人审、审到一半、返工中、看完待合并的需求，这样我不用逐个项目翻。
8. 作为验收的人，我想待审按风险条件依次排序，并把命中的条件显示成标签，这样我知道为什么这条排在前面，而不是面对一个看不出来源的分数。
9. 作为验收的人，我想点一行就进入那个需求的审查页、默认打开导读，这样我从该看的地方开始。
10. 作为等着审查版本算完的人，我想还没算好的需求显示「未计算」并已经开始算，这样我打开时通常已经有 diff。
11. 作为需求进入 awaiting-review 时的人，我想飞书「可以来验收了」链到审查页，这样我不用先去交付页再跳。
12. 作为每天看早报的人，我想早报文末链到待审，并且返工中的需求（包括曾经验收过、此刻又在收尾的）也在早报里，这样修改要求和追加票第二次收尾不会从早报里消失。
13. 作为第一次收尾还没开完 PR 的需求，我不想它出现在待审或早报里，这样「返工中」不会把正在开 PR 的第一次收尾算进去。
14. 作为打开审查页的人，我想需求标签栏多一个「审查」，交付页每个 PR 卡片有「审查代码」，原来的托管链接仍在，这样我既能看平台 diff 也能去托管合并。
15. 作为打开审查页的人，我想先看到导读：需求在做什么、User Story、按依赖序的每张票、收尾、修改要求、设置和规划提交、没有归属的改动，这样我按故事读，而不是面对一棵文件树。
16. 作为读导读的人，我想每张票那一节有它负责的 User Story、验收标准和验证状态、agent 当时写的 summary、它记下的决定、以及它改的 hunk，点 hunk 就跳到对应代码。
17. 作为读导读的人，我不想看到失败或没有输出的运行被补写的说明，这样导读里的话都来自当时做这件事的 agent。
18. 作为读多仓库需求的人，我想这份导读只列本仓库有改动的票，并注明别的仓库的票在哪个 PR，这样我不会以为 T-305 改的是眼前这个 diff。
19. 作为读导读的人，当有改动对不到票时，我想顶部写明有 n 段没能对上，并在最后一节列出它们，这样我知道漏了什么。
20. 作为按票看代码的人，我想文件树可以按票分组，点某张票下的文件时只高亮这张票的 hunk，其余折成「另有 2 段属于 T-302」。
21. 作为按目录看代码的人，我想文件树也可以按目录分组，和托管上的习惯一致。
22. 作为找文件的人，我想用 `/` 按路径过滤（支持通配），并把未看、有意见、有草稿、上次审后改过、新增/删除/改名、属于某张票、只看测试、隐藏生成文件做成可多选的过滤，条件留在 URL 里。
23. 作为看已看进度的人，我想「已看 x/y」始终按全部文件算，过滤后另写「当前显示 n 个」，这样过滤不会假装我看完了。
24. 作为看 generated 和 lockfile 的人，我想它们默认折叠并显示行数；测试文件不折叠，因为门禁要看它们。
25. 作为看超大或二进制文件的人，我想页面写明省略原因并给托管链接，而不是空白。
26. 作为看不完整 diff 的人，我想顶部写明「这份 diff 不完整」，并且不能显示成全部看完。
27. 作为要对着代码看需求的人，我想右栏有合并前清单（待人定、未验证的验收标准、CI 和冲突、合并顺序、自动合并预告、本 PR 的人审意见）、需求与票、Finding（按票关联，不挂行号）。
28. 作为对照验收标准的人，我想右栏「需求与票」列出票负责的 User Story 和验收标准的验证状态，数据来自票上的 stories、需求正文和验收包，验收包本身不新加 stories 字段。
29. 作为看完一个文件的人，我想勾「已看」；同一个文件内容没变时，新的审查版本仍算已看，内容变了就失效。
30. 作为用键盘的人，我想只在审查页用 `j`/`k` 换文件、`n`/`p` 换 hunk、`v` 切已看、`c` 写意见；这些键在别的页面不生效；帮助 `?` 有「审查页」一节。
31. 作为人正在看时 PR 又推了新提交的人，我想看到横幅「PR 有新提交：切换到 …」，内容和行号不自动换，这样我写到一半的意见不会对错行。
32. 作为展开上下文的人，我想 hunk 上下展开 20 行或展开到下一个 hunk，内容来自已经存下的 blob，不再排作业；太大没存的文件告诉我去托管看。
33. 作为返工后再看的人，我想切到「上次审后」只看被改过的文件，导读多一节「修改要求 #k」列出意见原文、处理结果和 Rework 改的 hunk。
34. 作为写意见的人，我想点行号写一条、在文件头写一条、在 PR 层面写一条；意见先是草稿，只存在平台里；编号是 C-n。
35. 作为改草稿的人，我只想在需求 awaiting-review 时能写、改、删草稿；其他状态只读；需求取消时草稿删掉，已经提交的留下。
36. 作为提交修改要求的人，我想一次提交当前所有草稿，需求进入 finalizing，有意见的仓库跑 Rework，所有开着的 PR 转草稿，自动合并停掉。
37. 作为误点两次提交的人，我不想建出第二个修改要求，第二次应被拒绝。
38. 作为在旧审查版本上写过草稿的人，我想提交时被要求确认「意见写在旧 head 上，agent 会看到写下时的那几行」；确认后照常提交，Rework 上下文带 writtenOn。
39. 作为部分合并后还想改的人，我想提交被拒绝，并看到要另建指向原需求的 bug 需求，而不是再走修改要求。
40. 作为返工还没结束时又想提交的人，我想被拒绝并看到「正在返工，等它结束再提交」。
41. 作为 Rework 的 agent，我想读到这次修改要求里本仓库的每条意见（编号、写下时的版本、位置、excerpt、正文）和当前 head，这样我能对着代码改。
42. 作为 Rework 的 agent，我想每条意见都交代 addressed 或 declined；缺 id、多 id 或不认识的 id 是非法输出，走现有的结果格式修复。
43. 作为 Rework 的 agent，当意见要求改保护路径或删测试名时，我想写成 declined 并记一条 conflict，而不是 cannot-proceed，因为没有一张票能让人批准这次 Rework。
44. 作为 Rework 的 agent，当意见和需求、契约或现有测试冲突，或 excerpt 在当前代码里找不到时，我想 declined 并说明原因。
45. 作为等人的人，当 Rework 改了已有测试或测试/构建配置时，我想走 Recheck，和 final-fix 一样。
46. 作为等人的人，我不想修改要求重跑 final-review 或 Tidy，审这次改动的人就是我。
47. 作为联调需求的验收人，当 Rework 改过集成分支时，我想开 PR 前再跑 e2e；提交修改要求和在 awaiting-review 追加时都删掉旧的 final e2e 行，这样第一次收尾的 done/waived 不会让第二次跳过。
48. 作为看验收包的人，我想仓库那一节最前面是人审意见：多少已处理、多少没处理，没处理的进待人定。
49. 作为看托管 PR 的人，我想看到一条平台维护的汇总评论（提交时标处理中，结束后改成逐条结果），按标记更新同一条，失败不挡流程，审查页写明没写上。
50. 作为 GitHub 上的平台运营，我想接入检查把 Issues 写当成必需权限，缺了就和缺 Contents 写一样挡确认，并给出修复链接。
51. 作为看 `plat spec show` 的人，我想多一行人审意见条数（待处理 / 已处理 / 没处理）和最近一次修改要求的状态，但不想 plat 再做一份待审列表。
52. 作为开了自动合并的项目，我想有已提交人审意见的需求永远不再自动合并，预告写「平台上有人审意见」。
53. 作为开了自动合并的项目，我想 worker 在改描述和合并之前重读 PR：已经不是 open、成了草稿、head 不是预期 SHA、有人评论、或 review 是 changes-requested，就失败返回，不改描述也不合并。
54. 作为看交付页的人，当项目是 manual 时，我想看到「按这个顺序合并，平台不会合并」；当项目是 auto-improvement 时，我想看到「按这个顺序合并；满足条件时平台会自动合并」，后面仍是原来的自动合并预告。
55. 作为返工中在托管上合并了其中一个 PR 的人，我想需求进入 merged，剩下的收尾作业和 Run 停掉并清理，和追加票返工中合并 PR 一样；第一次收尾（从未 awaiting-review）不走这条。
56. 作为第二次修改要求的人，我想用新的 Rework 分支名，清理时删掉这个需求所有 rework 分支。
57. 作为看审查页的人，当 PR 的 head 只往前走、状态没变时，我想页面经 SSE 刷新并出现切换横幅，而不是一直显示旧 SHA。
58. 作为安全上的约束，我不想网页、作业参数和日志里出现令牌；审查页只能用属于这个需求的 PR 和属于本平台审查版本的 blob；worker 不连数据库；agent 只读 /context。
59. 作为槽位被 agent 运行占满时打开审查页的人，我想审查版本计算和 host-sync 仍能被领走，因为有一个只领不占槽位作业的循环。
60. 作为 merged 或 cancelled 九十天后的追溯者，我想意见和修改要求还在，但 diff patch 和不再被引用的 blob 已被删掉。

## Implementation Decisions

- 人审意见以平台为准（ADR 0012）。托管上只放一条 bot（或 GitLab 令牌本人）维护的汇总评论，不算进 humanComments。不接个人 OAuth，不逐条同步成托管行内讨论。
- 新术语：Review comment、Change request、Rework、Review revision、Review guide、Review queue。人审意见不是 Finding。Rework 不是 Ticket，也不是需求状态 reworking。
- 需求状态机增加 `request-changes`：awaiting-review → finalizing；以及 finalizing → merged（仅当该需求曾经进入过 awaiting-review）。不能复用现有的 rework 事件（那是追加票 → reworking）。
- 收尾步骤增加 rework。Rework done 之后走 final-merge，命中 Recheck 条件时先 Recheck。这条路上不跑 Tidy。Rework 的 conflict / known-gap 不经 Spec 轴裁定，直接进验收包待人定。
- 审查版本由 worker 用 git 对 merge-base(默认分支, head)..head 计算，托管只提供 SHA。生成文件名单读该 head 的门禁配置。作业键按 pull id + head SHA 带序号；同一 head 已 ready 不再排，failed 再排写回同一行。超限的文件省略 patch 并标明原因。
- 已看按 blob 记，不按人记（尚无登录）。人审意见钉在写下时的审查版本上，带 excerpt，新版本不重新定位。
- 测试文件和 lockfile 在算审查版本时写成布尔标记（路径启发式）；生成文件仍只认门禁配置的 generated。既是测试又是生成文件时按测试，不默认折叠。
- 导读由 API 用已有记录和逐行归属拼出，按审查版本缓存，不跑 agent。票的 User Story 分配读票上的 stories 和需求正文，不写进验收包。
- 待审「返工中」= reworking，或 finalizing 且事件表里曾经 to_state=awaiting-review。第一次收尾不进待审、不进早报。
- 提交修改要求时：锁住需求、草稿改 submitted、有意见的仓库排 rework、所有开着的 PR 转草稿、停自动合并、删除该需求的 final e2e 行、排汇总评论。在 awaiting-review 追加时同样删除 final e2e 行。
- Rework 分支名为 agent 下的 `S-<n>-rework-<k>`，每次修改要求新名字。保护路径无票级豁免。意见要求改保护路径或删测试名 → declined + conflict，不 cannot-proceed。
- GitHub App 增加 Issues 写，汇总评论走 issue comments，按 HTML 标记更新同一条；不改用 Pull Request Reviews API。接入检查把 Issues 写列入必需权限。GitLab 用 MR notes。换 token 时 review-note 申请 Issues 写和 Pull requests 写（只申请 Issues 写时 GitHub App 不能在 PR 上发 issue comment）。
- 自动合并预告在平台已提交人审意见数大于 0 时否决，以后也不再自动合并。worker 合并前重读 PR。
- pull_requests 在 head SHA、与默认分支冲突、humanComments 变化时写事件（与现有 draft/ci/review 同一套路）。审查相关表同样由触发器写事件。host-sync 作业本身仍不记事件。
- worker 多一个只领不占槽位作业的循环，避免槽位被 agent 占满时审查版本算不出来。
- 显示编号增加人审意见 C-n。

## Testing Decisions

只测外部行为：HTTP、CLI 输出、导出的纯函数、页面通过假 HTTP 看到的文案和跳转、worker 托管任务的交回结果。不测私有方法、内部调用次数、React 内部状态。API 连真 Postgres；GitHub / GitLab HTTP、agent 运行器、时间用边界假对象；git 用临时仓库真跑。

接缝（沿用现有，不新开一层）：

1. **HTTP API + 真 Postgres**（现有 `*-api.test.ts` / `createRoute`）：待审分组和风险排序、审查版本生命周期、已看、人审意见草稿、提交修改要求（含旧版本确认和各状态拒绝）、final e2e 行删除、自动合并预告、接入检查缺 Issues 写、head SHA 变化写事件。这是主接缝。
2. **Worker 托管任务**（现有 host 任务测试 + 假 GitHub/GitLab + 临时 git 仓库）：审查版本的清单/归属/上限与 `git diff --raw` 一致、不执行 diff.external/textconv、自动合并前重读 PR 后不改描述也不合并、汇总评论按标记创建或更新、槽位满时不占槽位的作业仍能被领走。
3. **已导出纯函数**（现有状态机、收尾步进、自动合并预告、显示编号测试）：request-changes 与 finalizing→merged、rework 步进与跳过 Tidy、有人审意见则否决自动合并、测试/lockfile 路径启发式、C-n。
4. **控制塔页面经假 HTTP**（现有需求页、工作台、快捷键测试）：交付页按合并策略的文案、待审入口和角标、工作台摘要、审查页过滤/已看/导读跳转、审查页内快捷键不在其他页生效。
5. **`plat spec show`**（现有 CLI format 测试）：人审意见那一行。
6. **Rework 结构化输出**（现有 agent 结果 schema 测试）：comments 必须覆盖上下文里每个 id，否则 invalid-output。
7. **通知和早报**（现有通知与早报测试）：可以来验收了链到审查页；早报口径与待审「返工中」一致，文末链待审。
8. **合并出口守卫**（现有 guards 测试）：合并调用仍只在自动合并那一个出口。

追加票返工和修改要求 Rework 两条路上，下列行为都要在对应接缝上测：人在托管上合并 PR、返工结束后重建验收包并转回 ready、删除 final e2e 行、自动合并不在返工中或返工后发生、待审出现在「返工中」。

演练（Mac 上 3000 端口平台，GitHub 与 GitLab 各一次）不属于自动化接缝，做完把测量写回技术方案。

## Out of Scope

- 在平台里合并 PR（ADR 0011 只有一个出口；GitLab bot 合不了受保护分支）。
- 用人的托管身份提交正式 Review、逐条同步行内讨论、个人 OAuth。
- 拉托管上评论的正文（页面只显示条数和链接）。
- 人审意见自动生成追加票。
- 只留记录、不交给 Rework 的「纯评论」（不提交草稿即可）。
- 并排对照、语法高亮、给 Finding 加文件和行号。
- 暂缓待审、按审查人区分已看（尚无登录）。
- plat 上的待审列表命令。

## Further Notes

- 实现前在 GitHub App 设置里把 Issues 改成 Read and write，再合入接入检查那张票并重启本机平台，否则每天的仓库检查会报缺权限。
- 意见涉及新行为、契约或跨仓库时，仍用追加票，不走修改要求。
- GitLab 上 humanComments 不计令牌本人；项目用的是人自己的 PAT 时，人在 MR 上写的评论不挡自动合并。现在 GitLab 不自动合并，记在这里。
- 界面参考 Linear 的 Reviews 收件箱、Guide、Since last review、已看按内容失效；风险不用单一分数。
